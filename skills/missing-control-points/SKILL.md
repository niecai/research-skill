# Missing Control Points

「看起来像了但细节不对」的诊断 skill。是 [`top-down-debugging`](../top-down-debugging/SKILL.md) 在
「产物级控制点缺失」场景的具体化 —— 先画控制层、找缺失/错位/越层的控制点，再动手。

> **本 skill 只放方法论与领域中立的控制点模式。** 不写任何具体项目 / 产品 / 技术栈的实例、
> 标识符、文件路径、偏移、协议名。需要举例时用抽象占位（「某资源」「某 ID」「某容器对象」），
> 不暴露具体是什么系统。看到下文出现具体领域术语，那是 bug、应删。

## 何时使用

满足任一条件就用：

- 「主体基本对了，但某个细节（位置 / 朝向 / 时序 / 附属属性）不对」
- 「某个效果 / 资源 / 校验复制过去了，但运行时不响 / 不生效 / 挂错位置」
- 「同一份产物在某些上下文（不同场景 / 角色 / 区域 / 网络态 / 权限）有效、某些无效」
- 怀疑「不是参数问题，是算法缺项 / 数据没传到下游 / 运行时上下文不对」
- 你发现自己开始反复改「入口 / 状态 / 触发条件 / 局部参数」来猜问题

## 目标

先回答这句：

`working 成品 比 当前失败产物，多做了哪一步数据传递，或多了哪个运行时前提？`

不要先回答「再换一个入口」「再改一个状态」「再试一下触发」。

## 强制输入

开始前必须明确 3 个对比对象（= top-down 四方对照去掉 layer model）：

1. `working`：已知正确的成品（成品参照 / baseline / 上线正常版本）
2. `failing`：当前失败产物
3. `source / reference`：源输入、源资产、规格、目标行为标准

没有这 3 个对象，不要进入昂贵的运行时实验。

## 控制点分三层查

按层从上到下，每层都对着 `working` 做**完整对比**（不是抽查 —— 见 top-down 模式 F：
抽查一层就宣布无罪会害你白挖深层）。三层是领域中立的抽象，落到任何具体产物上都能映射：

### A. 核心资产 / 算法层

产物本体的「生成算法」缺项：核心数据被错误归一化 / 错误塞进别的字段 / 范围量级不对 /
本该进输出的中间结果没进 / 主时序（长度、节拍、循环点）与目标不匹配。

判法：把 `working` 和 `failing` 的**核心字段**逐项 diff，量级对齐到 `source`。

### B. sidecar / 元数据层

附属于主资产、驱动它如何被消费的那层：辅助事件、校验、时序标记、映射表、缓存、索引、
标签、锚点、权限位。常见两个坑：

1. **跨上下文复制要 remap，同上下文不用**
   - 附属事件里引用「位置 / 对象 / 锚点」的参数，往往是**相对某个命名空间的 id**
   - 源与目标是**不同主体**：必须 remap 这些 id，否则挂错对象
   - 源与目标是**同一主体的不同实例**：id 已同套，**不要** remap
   - 分清 `replace`（先删目标同类再拷）和 additive（直接追加、会和原有同类叠加）
2. **附属事件复制对了仍不生效 ≠ sidecar 缺项** —— 升层查 C 层运行时上下文

### C. 运行时上下文层

「产物全对了，运行时就是不生效」时查这层。上下文 = 场景 / 角色 / 区域 / 网络态 /
资源加载状态 / 权限 /**你自己代码里的 routing gate 条件**。这层最 subtle，是反复打转的高发区。

- **资源加载状态**：某资源（库 / 模块 / 对象 / 子系统）只在特定上下文加载、别的上下文卸载 →
  卸载态里引用它的产物全失效。资产层完全正确也没用。解法是让你的代码自己 **force-load**
  那个资源（⚠️ force-load 的接口参数 / 数据结构布局要对着接口文档查准，靠猜会卡好几轮）。
- **ID 相对性（最易忽略的陷阱）**：运行时的 ID / handle / index 可能不是绝对的，而是
  **相对当前上下文**。同一个数字 ID 在不同上下文（不同 session / 不同加载顺序）解析到
  **不同对象**或**直接 NULL**。两种典型：
  - **别的对象占了 slot**：原 owner 卸载后、另一对象重用同 ID → 解析出**别的对象**（表现为
    「错的结果」而非「无结果」，更难发现）
  - **slot 变 NULL**：没经过那个 owner active 的阶段就直接进新上下文 → ID 对应的 slot = NULL →
    下游解引用空值 → 崩 / 被守卫拦成 未找到
  - 根因常是：这个「ID」其实是**某内部数组的下标**、不是 namespace map / hashtable。数组下标
    对「卸载-重载」场景特别脆弱
  - 用 ID 取资源前先确认它在当前上下文有效；优先用「按名字 / 在特定容器对象内」的查找，少用裸全局 ID
  - **绕开相对 ID 的 fix 模式**：在边界处拦截（hook / 代理）、检 ID 落在 problematic range +
    detect 上下文不匹配 → **不转发给原查询**、改用「容器 + 名字」直接 lookup、返一个有效结果
    给调用方。调用方收到有效结果就不进入 空引用 / 失败计数 累积路径
- **查询层级**：资源常是分层的（系统 → 容器/分组 → 叶子）。按名字 / index 查不到（未找到）时，
  先确认你查的是不是**正确的层级** —— 在父层查叶子会找不到。要么换叶子所在那层的查询接口，
  要么先**枚举对象树**把结构打出来再定位。枚举本身是个 observer，能 settle「资源根本没解析出来
  （空壳）」还是「在、只是查错层」。
- **生命周期**：资源 / handle 的创建-使用-释放时机。working 和 failing 的差异可能只是
  「使用时刻还活着 vs 已被释放」。
- **⭐ 你自己代码的 routing / dispatch gate 条件（最容易排到最后才发现）**：你自己代码里的
  回调 / 分支 / phase guard / `if` 条件，本身就是一个**控制点**。当你怀疑「下游依赖 / 运行时深层
  有问题」时，**先 audit 自己代码里所有 `if 上下文==X / if 状态==Y / if 缓存==0` 一类 gate 是否
  正确覆盖了当前 failing 场景**。这步 cost ~0，能避免把方向投错到深层排查几轮。

判据：A/B 层全对（diff 无差异）但目标行为仍不出现 → 一定在 C 层（top-down 模式 G：这层全绿
目标还没达成）。**进入「深挖下游依赖 / 运行时深层」之前，必须先 audit 自己代码的 routing gate
是否覆盖当前 failing 场景** —— 自家代码 audit 几乎免费，能挡掉投错方向的几轮昂贵深挖。

## 禁止项

在离线 diff 出控制点前，不要做：

- 改「入口 / 状态 / 触发 / 局部参数」来猜问题
- 连续做昂贵的运行时实验（每次实测都贵）
- 基于「看起来合理」的推论直接做 modifying（见 top-down 规则 7：推论先交叉验证才能当 modifying
  前提；observer 优先于 modifying）

## 输出要求

先产出差异表，至少包含：

- 对象：`working / failing / source`
- 层：`A 核心资产/算法 / B sidecar 元数据 / C 运行时上下文`
- 控制点 + 现象（谁有谁没有、差异量级）
- 结论：补算法 / 补 sidecar / 补 force-load / 改 ID 取法 / 改生命周期 / 改自家 gate

差异表成立后才改东西。

## 修复优先级

1. **算法缺项**：核心字段 / 中间结果 / 主时序
2. **sidecar 缺项**：附属事件 / 时序 / 校验 / 锚点
3. **运行时上下文缺项**：资源 force-load / ID 取法（避开相对 ID）/ 生命周期 / 自家 routing gate
4. **最后才是更深的状态机 / 入口路径**（只在证明前三层完整后再碰）

## 可复用的控制点模式（领域中立）

下面是从多轮实战里提炼、跨领域都成立的具体模式。每条都是「某次在错误层级打转、最后发现真控制点
在别处」的抽象。

### 模式 1：自家 routing gate audit 必须前置于深层依赖深挖

怀疑「下游 / 运行时深层有 bug」时，先把自己代码里所有路由 / 分支 / phase 条件列出来，逐个对当前
failing 场景验「这个 gate 是否把当前场景排除了」。深层深挖每轮 cost 几个工作单元；自家 gate audit
cost ~0。**真因常常就是自己 hook 里 1-2 行的 phase 排除条件，却投了多轮去挖下游。**

### 模式 2：trace 字段做频率 diff 优先于 narrative 推论

silent / 失败 vs 正常 两组观测对照时，**先按顶层标签 / 事件名做频率 diff**（哪个计数在失败组
是 0、正常组非 0），再深挖底层。一个「某计数在失败组恒为 0、正常组恒为某值」的 1:1 信号，常常
直接指向真控制点 —— 但如果 narrative 早早锁定「真因在深层」，看的字段都偏深，就会长期错过这个
顶层信号。

### 模式 3：baseline-in-same-context 可能要测多个 baseline + 多种触发

「改动后出现的故障」要回滚到改动前在**同一场景**复现（top-down 模式 J）。但有时一个 baseline
不够 —— 真正的 working 可能依赖**特定的触发路径**（直接进入 vs 经由另一条路径进入）。要测
**多个历史 baseline × 多种 trigger 组合**，才能 isolate「真 working 是哪条 path 触发的」。
接手任务时别人「偶然提到的曾经 working」必须先 systematic reproduce，不能直接当 working baseline 接受。

### 模式 4：多计数 1:1 相等 ≠ causation（disable 对照）

两个计数每个采样点都相等，直觉「A 触发 B」。但它们可能各自独立累积到同一 ceiling、都受同一**上游
cause** 影响。验证 = disable 其中一个的 source、看另一个是否仍累积到同一数字。是 → 1:1 是 coincidence、
真因更上游。（top-down 模式 L 的工程形态。）

### 模式 5：贵 modify-loop 连续失败 → 强制转离线深挖

连续 N 轮「改一版 → 部署 → 复现 → 推翻 narrative → 再改一版」（每轮都贵：重建 / 重启 / 等人实测），
每轮 modifying 自己都成功执行但目标没达成 —— 这是 narrative 缺结构信息的信号。强制**暂停 modify-loop、
做一段离线深挖**（读源 / 反推数据结构 / 走调用链 / 看相邻系统）。离线深挖 vs modify 迭代的 leverage
常差一个量级。用户说「你每次重启都出 bug、得多离线分析」是外部 trigger —— 不辩护、直接 pivot。
（top-down 模式 N。）

### 模式 6：canonical fallback 验证 feasibility > 设计 perfect mapping

要验「整条 path 是否走得通」时，用一个**硬编码的已知可用值**当 fallback 先打通，verify 后再 refine
成精确映射，比一上来就设计 perfect mapping 快得多 settle。perfect mapping 还容易踩跨边界的
namespace mismatch（lookup 全 miss）—— 建 map / cache 前先 verify key 的 namespace 跟 lookup 端
用同一套。

### 模式 7：改变数量 / 尺寸的容器操作要警惕「重建索引」的未验证代码路径

复用一个「在 overwrite 用途上一直没问题」的工具去做 add / insert / delete / resize —— 这些会触发
**重建索引表 / 偏移 / 计数**的代码路径，而「同尺寸 overwrite」用途永远不触发那段重建逻辑、所以那段
可能是**带 bug 的未验证死代码**（top-down 模式 U）。决定性的离线验证 = **unchanged-input 字节恒等**：
`serialize(parse(x)) == x` 对未修改的 x 必须 byte-identical；连不改都不恒等，函数就是模型错的，改了
只会更错。这个测试纯离线、零成本，在做任何 modify 实验前就能抓出「重建逻辑写错了哪个字段」。

### 模式 8：workaround「能跑」≠ 满足真实需求里那条难点对应的属性

真解卡在一个难点上（崩 / 没通 / 贵），找了个绕开难点的 workaround、它能跑结果看着对，就当交付了 ——
但 workaround 往往靠**复用 / 寄生 / 共享**已有东西达成，**没满足需求里那条「难点对应的属性」**
（独立性 / 隔离性 / 可扩展性 / 所有权）。验收要回到**原始需求的每条属性**问「workaround 给的是哪个」。
那个被绕开的难点，常常**正是**需求里最关键属性的来源。workaround 可作临时证明，但要明确标注「不是交付」、
把真难点继续列为必解。（top-down 模式 V。）

### 模式 9：源拷贝污染 —— 复制一个资产时，藏在它里面的属性会原样带过来

从 A 复制一个资产到 B 时，往往**只有部分层转移**（如只转主数据 + sidecar、不转更深的图 / 配置）。
所以源里「藏在没转移那层的属性」不会过来；但「藏在转移了那层里的事件 / 标记」会**原样带过来、在 B
上语义可能完全不同甚至致 bug**。复制一个东西后出现「多出来的行为」，第一站查**源比目标 working 参照
多了什么 sidecar 事件 / 标记**，对照删。

### 模式 10：运行时清框架 flag = 竞态必败，真修复在数据源

很多框架状态是**每个周期从描述符重建**的；你在运行时清它必输（清不赢重建）。定位那个 flag（控制点分析）
有价值 —— 确认是哪个 flag；但**修复点不在 flag、在喂给框架的数据源**（描述数据 / 状态分类 / 配置）。
原则：**让框架每个周期自己做对，而不是每个周期去纠正框架。**

### 模式 11：broad-cut-then-bisect —— 先整体禁掉嫌疑子系统坐实因果，再 split-gate 二分到精确元凶（保住有用部分）

怀疑某个**自己引入的子系统**是某个间歇性故障（死锁 / 崩溃 / 降级）的根因、但它由多个耦合组件构成、
且**故障一旦发生就无法在线解开**（如死锁后开关失效）时：

1. **broad cut（粗因果切分）**：从启动就**整体禁掉**整个嫌疑子系统（所有组件一起关），跑到平时故障
   出现的时长。不再故障 = 坐实是这个子系统；仍故障 = 子系统洗清、升层去别处。⚠️ 必须**从启动就关**
   —— 故障后才关无法解开已经发生的死锁 / 已孤立的锁。代价：暂时丢掉这个子系统提供的有用功能。
2. **split-gate bisect（拆开二分）**：坐实后，把子系统拆成**多个独立编译期 / 启动期开关**，按「哪个
   组件最可能是元凶」的先验，开**有用但无辜**的组件、关**嫌疑**组件。若故障消失且有用功能还在 = 找到
   精确元凶、且**保住了有用部分**（不是「功能换稳定」的取舍，而是定位到具体有害子路径只关它）。
3. 选哪个组件先开先关，用**故障指纹**（故障发生前最后一次活动落在哪条代码路径 / 哪个调用点）做先验 ——
   指纹指向的那条路径就是第一个该关的嫌疑组件。

关键判据始终是一个**客观的、与主观体感独立的连续量**（如某个心跳计数器是否单调推进 vs 冻住）——
故障 = 它冻住而其他进度仍推进。靠它客观确认每次实验「故障有没有真消失」，而不只靠「这次没遇到」
（间歇故障单次 non-repro 不算数，见模式 12）。

> 这是 top-down 规则 4（单变量）+ 规则 5（升层）+ 模式 N（贵循环转离线）在「自引入子系统致间歇故障」
> 上的合成：先用一次 broad cut 把「是不是我」一刀切清，再用 split-gate 把「是我的哪部分」二分出来 ——
> 比逐个组件试错快、且天然导向「保住无辜组件」的精准修复。

### 模式 12：间歇故障 —— 单次 non-repro ≠ 修好，单次 repro 的伴随现象 ≠ correlate

故障间歇出现时，跑一次没复现就宣布「修好了」是 inconclusive 不是 success；抓到一次复现就把当时
**碰巧同时出现**的现象当 correlate / cause 也不可靠。正确姿势 = **先投资可常驻的低成本观测**
（计数器 / 日志、不改行为），在**多次自然复现**里收集，看伴随现象是否稳定共现（≥2 次独立复现）。
别靠「改一版 → 测一次 → 看复现没」的高成本循环（那会撞模式 5）。（top-down 模式 P。）

### 模式 13：「整体按常数因子偏移 / 拉伸」的指纹 → 去数据找标度 / 时长元数据，别挖运行时

某个**随时间演化**的产物（时序回放 / 多路同步流 / 采样流 / 增量更新流）经过转换 / 重打包后，表现出
「事件**整体延后或拉伸一个近似常数倍**、且**末段按比例被截断不出现**」时：

- 直觉会往**运行时**找（消费方滞后、消费方丢样、某阶段卸载失效），越挖越深。但「均匀 ×k + 末段截断」是
  **标度元数据被设错**的典型指纹：某个 `duration / sample-rate / timebase / 单位` 字段被写成了 k 倍，消费方按
  `index = t / field × (N−1)` 取样 → 整体 1/k 速（k=2 就是半速）、`t` 到头时只消费了 1/k 的样本 → 末段永不被消费。
- **决定性定位（纯离线、零成本）**：拿**已知正确的源**和**你的产物**，dump **同一个标度字段**逐项对比 —— 源相等、
  产物 ×k 就锁定是它。比任何运行时实验都便宜一个量级（呼应 top-down 模式 Z：根因在数据、不在运行时）。
- **找对测量轴才看得穿**：用**消费方真正依据的那个量**当 x 轴（它内部的消费 / 进度游标），不要用你顺手的采样序号 /
  墙钟 —— 后者和真实轴差一个速率，会把这个「常数 ×k」伪装成「逐步滞后 / 某段莫名丢失」的运行时玄学，诱你深挖错层。
- **配套 control-point**：观测这类时序时，trace 的 gate 条件要挑**全程不变的稳定标签**（如产物 / 流的标识），别挑
  **会中途切换的瞬时标签**（如阶段 / 状态）—— 后者会在切换点把 trace 截断成**假阴性**（「末段不动」其实是 trace 停了，见模式 2 旁注 / top-down 模式 T）。

### 模式 14：两个各自合法的同层兄弟在「同刻 / 同独占 slot」共存时互相湮灭

两个附属元素（事件 / 校验 / 触发 / 写入 / 信号）各自对照 working 兄弟**逐字节 / 逐字段都合法**、链路也都对，
但当它们**同时**作用于**同一个只接纳单一占用者的运行时资源**（同一时间窗 + 同一锚点 / 同一单占字段 /
同一独占 channel）时，框架只仲裁一个、甚至两个都被丢弃 → 目标不生效。

- **诊断指纹**：你把失败元素和一个 working 兄弟逐字段 diff、发现**只差无关紧要的几个值**（甚至完全等价），
  于是反复确认「它没错」——对、它**单独**没错。真控制点不在元素**自身**、在「它和另一个元素**同刻同位**」
  这条**关系**上。单元素 diff 永远 settle 不了关系层的冲突。
- **诊断手段**：把同层所有同类元素按「作用时刻 + 作用位置」**分桶**；**同一桶里 >1 个独占型元素 = 冲突嫌疑**。
  working 参照里这种桶往往只有 1 个占用者（或第二个是**不同机制 / 占不同 slot**、不争用、所以不冲突 ——
  这个「看着也同刻、但不冲突」的对照正好反向确认冲突条件是「同**独占**资源」而非单纯「同刻」）。
- **修复是解耦、不是改值**：错开时刻（stagger）、串行化、去重、或分到不同 slot。改任一元素的「值」都没用 ——
  它们的值本来就对。这条要**通用化进主流程**：转换 / 合并 / 批量生成同类元素时，自动检测并解耦「同桶多占用者」。
- 跟模式 9（源拷贝污染）相邻：9 是「复制带进一个**多余**的 sidecar、删掉即可」；模式 14 是「两个**都合法、
  都该在**的元素因同刻同位而互斥」。跟 top-down 模式 X（多独立源）对照：X 是各自单独都致症（删一个不够）、
  模式 14 是各自单独都**无害**、只有共存才致症 —— 两者都在「组合 / 关系」层、方向相反。（top-down 模式 AA。）

### 模式 15：删「看着死」的代码前，先在运行时 gate 上验「真死」——「逻辑搬走了」不是证据

症状：某段代码「看着没用了」（功能据说搬到别处 / 旧方案残留 / 注释说已弃用），就要删。但「看着死」「据说搬走」是 narrative、不是事实——代码可能**每个周期仍在跑**（仍被主循环 / 轮询线程接线调用）、只是当前**无效果**。直接删可能改了行为而不自知。

- **真正决定「有没有效果」的控制点常在运行时上下文层**：它读的那个**外部配置 / 数据**的**实际内容**，加上代码里的**短路谓词**。典型形态：一段每个周期执行的逻辑，只有当它读的配置里某值越过阈值才产生效果；而该文件当前所有值都被一条 skip 谓词跳过 → 运行时 no-op。**「当前配置内容 + skip 谓词」才是「真死」的证据**，不是「功能搬到别处了」这句话。
- **反向同样成立**：判一个**模块 / 子系统**「没人用了、可删」时，grep 到引用 ≠ 它还活着 —— 引用可能**全在已永久禁用的块里**（`if false` / 编译期关掉的 cfg 分支 / unreachable）。这种引用让符号**看着被用**（编译过、grep 到），实则**永不可达**。删它前要对**每个引用点**确认「这条引用在不在死块里」；若所有引用都在死块 → 符号本身就是死的（先把那些死块也清掉，引用归零后再删模块）。
- 处理（删前三步）：① **全量 grep 该符号的所有引用**，特别是它仍被主循环 / 调度线程**接线调用**的点（这些不会因"逻辑搬走"消失）；逐个看引用是否在死块（上一条）；② **读它依赖的运行时 gate 的实际内容**，确认当前确实 no-op；③ 区分**死分支**与**在用外壳**——同一函数里可能另有在用分支，只删死的那条 + 它专属的 helper / static，保留外壳。删完编译 + 逐符号 grep 确认**零悬挂引用**（含被删函数曾用、现也该删的孤儿 helper）。
- **⚠️ grep / 静态审计只覆盖你能检视的层**：判「没人引用、可删」时，若系统里有一个**不可检视的层**（二进制 / 黑盒 / 编译产物 / 外部系统内部状态）仍引用这个元素、你的 grep 照不到它 → 删了在更晚的运行时点崩。**「在能读的层里看着 orphan」≠「真没引用」**。这类元素往往是**承重的**：它在不可检视层有引用、而动那个层的代价极高（二进制黑盒可能根本没安全编辑工具）→ 正确决定是**留着**（标注「inert 但被不可检视层引用、动不了」），不是硬删。一个之前被标「harmless 留」的孤儿，常是有人已撞过这堵墙的记录。删它前先确认：① 系统所有层里有没有你 grep 不到的；② 删一个的「结构完整性检查通过」**不证明**它没人引用（结构 ≠ 语义）；③ 唯一可信验证是在「会暴露悬挂引用」的运行时点删一个验一次、别批量删（top-down 模式 HH）。
- 与模式 10 相邻：10 是「运行时清框架 flag = 竞态、真修复在数据源」；本模式是「判**死活**也要看运行时数据源（配置的实际内容）、别信代码注释 / narrative」。两者都把判断锚到**运行时真实状态**而非源码表面叙述。

### 模式 16：元素本身合法、却没被登记进 runtime 真正迭代的那个集合 → 静默跳过、永不生效

一个元素（事件 / 条目 / 节点 / handler / 资源）**内容完全正确、放在对的文件 / 对的位置、覆盖也齐全**，但它**不是 runtime 实际遍历处理的那个集合（组 / 列表 / 表 / 注册表 / 索引）的成员** → 框架枚举那个集合时**根本不碰它** → 它静默地不生效（不触发 / 不响应 / 不生效 / 被跳过），且**不报错**（它没坏、只是没"入列"）。

- 这是「**注册 / 归属**控制点」：很多 runtime 不是"扫描所有存在的元素"、而是"遍历某个**显式成员集合**"。元素存在 ≠ 元素被处理；**成员资格**是一个独立于元素内容的 sidecar 控制点（模式 9 的源拷贝、模式 14 的同 slot 共存都在这层、但本模式是"压根不在集合里"）。
- 诊断：当一个元素"内容对、覆盖对、却不生效"、而**同类的别的元素生效**时，别再 diff 元素**内容**——去查它**在不在那个被迭代的集合里**。把生效的同类元素的**成员归属**提出来（它属于哪个组 / 在哪张表的哪行 / 被哪个 registry 收录），对照失效元素缺的就是这条（呼应 top-down 模式 S / CC：从 working 集提"归属"谓词）。
- ⚠️ **成员集合可能有多种、检查要查全**：同一类元素可能合法地归到**多个不同类型的组 / 表**（A 类元素在组类型 X、B 类在组类型 Y、两种 runtime 都处理）。判"丢失归属 / 没注册"必须把**所有有效集合**一起算；只查一种会**误报**(把在另一种集合里的当成没注册) + 修的时候**重复登记**(塞进第二个集合 → 重复处理 / 双重触发)。
- 修复 = 把元素**补登记进**一个有效成员集合（加进组 / 注册进表 / 插进被迭代的列表），不是改元素内容。**通用化进主流程**：任何**重建 / 转换 / 批量生成**这类元素的工具，重建后必须**保留 / 重建成员归属**、并加一个出厂检查「每个该被处理的元素都在某个有效集合里」——重建丢成员归属是这类静默失效的高发源。
- 例：一批"事件型元素"内容全对、覆盖全在，却不触发；同类的别的元素正常。真因 = 这批元素**掉了它们的"分组归属"**（某次数据重建丢的）、运行时只处理"在该组里"的成员 → 它们被静默跳过。修 = 把它们补回该组（不改内容）；并给重建工具加"成员归属保全 + 出厂归属检查"。

### 模式 17：变体 / 派生版维护成独立手工副本 → 必然漂移；改「单一源 + 程序化派生 + 同步断言」

一个产物需要多个**变体**（如完整版 vs 精简版、A 环境 vs B 环境、内部版 vs 发布版），变体之间只差**少数几条已知 delta**。若把变体维护成**独立的手工编辑副本**（各存一份、各自改），它**必然随时间漂移** —— 对「源 / 主版」打的修复 / 加的特性不会自动流到副本，副本**静默地少了那条**。

- **诊断指纹**：「变体 B 缺一条 A（源 / 主版）有的修复 / 特性」+「B 是一份手维护的拷贝」→ 漂移。缺失的控制点**存在于源、缺席于副本**，不是因为它从没被造出来（模式 16），而是因为**副本是个过期的复制品、不是派生品**。
- **真因不在「补上这一条」**：手动把漏的那条补进副本只是治标 —— 下一条修复又会漏。真因是「副本是独立副本」这个**结构**。
- **修复 = 单一源 + 程序化派生 + 同步断言**：① 只保留**一份**共享内容（单一源）；② 变体由**脚本从源派生**、只施加那几条已知 delta（删某些文件 / 翻某个编译开关 / 换某个配置值）；③ 加一条**出厂同步自检**：断言「变体里的共享部分 == 源**逐字节相等**」+「该被 delta 去掉的确实不在」→ 任何漂移**当场 fail**。源一改，所有变体自动跟，且「变体间只差这 N 条 delta」这条不变式被机器守住、不靠人记得同步。
- 跟模式 9（源拷贝污染）对照：9 是复制带进**多余**东西；模式 17 是**独立副本少了**后续更新。两者都源于「拷贝而非派生」—— 拷贝在两个方向都会出问题（带多余 / 缺更新），所以**能派生就别拷**。
- 排查时先问：「这个变体里看着缺的东西，它的**源 / 主版**有没有？源有、变体没有 = 漂移（结构问题），不是这一条本身的问题。」

### 模式 18：构建侧 —— 部署前逐层离线验证三层控制点，让第一次部署就对（别拿 deploy 当 build 的验证手段）

前面 1-17 全是**诊断**（产物坏了、回头找缺失控制点）。同一个三层模型**正向**用就是**构建纪律**：要造一个分层产物（核心资产 + sidecar 归属 + 依赖运行时上下文里某资源）时，**部署前**把三层各自离线验一遍，而不是 `build → deploy → 进运行时看 → 不对 → 改 → 再 deploy` 地循环（每轮 deploy + 运行时确认都贵：重启 / 等人实测 / 肉眼看）。

部署前的三层离线核对：

- **核心资产层**：你新造的核心数据块跟一个**已知能跑的同类模板逐字节比**，只该差你**有意**改的字段（id / 位置 / 参数）。模板里你不懂的隐藏字段**照抄、别自造**（呼应 top-down 模式 W：拿 baseline 的**事实形态**比，别按「应该长啥样」造；模式 BB：刻意不改的部分要 byte-identical）。
- **sidecar / 归属层**：构建工具**自检**「每个新元素都进了那个会被 runtime 迭代的集合」（模式 16 的归属 + 出厂检查），且**所有有效集合类型都查**（别只查一种 → 漏报 / 重复登记）。
- **运行时上下文层**：你引用的外部资源（库 / 模块 / 插件 / 依赖 id）**确实在目标部署环境的资源集合里存在** —— 离线 enumerate 目标环境那个集合、确认你要用的每个 id 都 present。这一步专防「资产全对、运行时那个资源根本没加载 / 不在这个资源包里」的 C 层失效（模式 16 的 runtime context、资源加载墙）。

- **校验清单本身要从权威源派生、别用手维护子集**：上面「每个 id 都 present」「每个新元素都入列」靠一份**清单**驱动；若这份清单是**手维护的子集**（你记得几个就列几个），它会**静默漂移** —— 产物新引用了一个东西、你忘了加进清单、校验照样全绿、漏的那个到运行时才暴露（模式 16 的静默跳过 + 模式 17 的副本漂移在「校验清单」上的合体）。修：让校验**从产物的权威引用集派生**（枚举产物**实际**引用 / 依赖的全部条目当清单），而不是比对一份人维护的「应该有这些」列表。一份「我以为要查这些」的硬编码子集，跟它要守护的真实依赖之间，迟早差出一个没人发现的缺口。

三层全绿才 deploy。这把「部署-观察-改」的**昂贵在线循环**换成构建前的**廉价离线核对**（每层 cost ~秒），一次 deploy 顶过去 N 轮 trial-and-error。

- 跟「禁止项」同源：禁止项讲的是**诊断**侧「离线 diff 出控制点前别做昂贵运行时实验」；本模式是**构建**侧的同一条原则 —— **离线验完三层再 deploy，别把 deploy + 肉眼看当成 build 的迭代 / 验证手段**（那是最贵的验证手段）。
- 外部 trigger：用户说「多离线、别一下子部署、思考久点」「你每次都在试」时，通常正是你把「部署 + 看效果」滑成了构建的试错循环 —— 立即转成「部署前逐层离线核对」。（与 top-down 模式 N「贵 modify-loop 转离线深挖」同向，但 N 是诊断卡住时转离线、本模式是**一开始构建就别进在线试错循环**。）

### 模式 19：控制点的「成员资格」由你改不了的系统管理 → 控制点上移到「调用它的那条可改指令（seam）」

- 形态：你要让某元素被 runtime 处理（加载 / 进入 / 生效），但**决定它进没进那个被迭代集合的逻辑在一个你改不了的系统里**。模式 16 是「成员资格是控制点」（你能改集合）；本模式更进一步 —— **成员资格你直接加不了**：元素文件 / 资源放进去了、runtime 却不处理，因为那个系统只在它自己的某条触发路径下才把它登记进集合。
- 路线：① **排除法坐实「开关不在数据层」**：基线 vs 改动版全量 diff 所有可改数据层（脚本 / 参数 / 布局 / 资源），确认**没有一处注册表 / 开关**控制它 → 不是你漏了某份配置、是那个系统硬编码的约定，别再找数据开关。② **找 invocation seam**：读「已知能让该元素生效的那个入口」（入口 / 脚本 / 事件的 handler），里面必有一条**让那个系统做这件事的可改指令**。③ **复用那条指令**：从你自己的入口调同一条指令 → 系统替你完成登记 + 激活。控制点不是「元素本身 / 配置」，是**那条 seam 指令**。
- 阴性陷阱：把元素放进去、探针不响 → 别下「不支持 / 机制不存在」，先在**那个系统已知会激活它的那条路径**上验探针（positive control，见模式 2 旁注 / top-down 模式 T）—— 多半是触发路径错了、不是控制点不存在。
- 与模式 16 / 18 配对：16 = 成员资格是控制点（你能改集合）；本模式 = 成员资格由不可改系统管（只能改「触发登记」的 seam）；18 的 C 层「资源在目标环境集合里 present」同理 —— 都在问「这元素到底由谁、在哪条路径上被纳入 runtime」。（top-down 模式 EE 是本模式的抽象版。）

### 模式 20：一个 layer 有多条平行「事件类型 / 通道」，检视工具只 surface 一种 → 穷尽那一种 ≠ 这层无罪

- 形态：你要在某 layer 找一个控制点（产生某效果 / 携带某行为的东西）。你用一个检视工具 dump 这层、**穷尽搜索了它显示的那一种** element-type（事件类型 / 记录类别 / 通道），没找到，于是判「不在这层」、升层或换方向。但这层里**并行存在多种 element-type**，目标控制点由一种你的工具**从没 dump 出来**的类型携带 —— 效果经由「另一条平行通道」产生，不是你一直盯的那条。
- 诊断：当「穷尽搜了某层的某类元素、没有」却仍确信效果出自这层时，先问：**这层只有这一种 element-type 吗？我的工具覆盖了所有类型吗？** 很多容器 / 时间线 / 事件流是「多类型并存」的（一种管 A、一种管 B、一种发射子单元……），通用 dump 工具常只解你当初关心的那一种。
- 修复 = **枚举该层的全部 element-type、逐类 dump**（或换一个覆盖全类型的工具），再判这层有没有目标。
- 关系：是 top-down 模式 F（一层没查完）的一个高发具体形态 —— F 泛指「没查完」，本模式特指「**整整一类平行通道从没被工具 surface 过**」。也接 top-down 模式 T（阴性来自没验证覆盖度的探针）：你的「没找到」只覆盖了工具会显示的那一种类型。配对模式 18（构建侧「所有有效集合类型都查」）：同一信条两端 —— **「一种」不等于「全部」，先确认你枚举的是全集。**
- **整块覆盖式替换会静默 remove / move 既有元素、不只 add —— 且净数量会掩盖。** 当故障来自一个「**整块替换某容器**」的操作（而非 base + 增量叠加）时，三方 diff 不能只看「加了什么」：要逐 element-type 查 **added / removed / moved / modified 四类**。**净计数会骗你** —— 「删 19 + 加 22 = 净 +3」看着只多了几个、其实换掉了一大片；真正破坏既有功能的常是被**删掉 / 移位**的既有元素（如被删的既有记录、被移位的引用点），不是新加的那些。**根治方向 = 别整块覆盖，改「base + 最小增量叠加」**（呼应模式 17 单一源 + 派生、模式 21 跨主体搬运）：整块覆盖一个共享容器 = 把该容器里**所有**既有功能都置于风险，只有当你的替换恰好保住每一条既有元素时才不炸。

### 模式 21：跨主体搬运一个产物 = 整条依赖链都要重建 / 重锚 / 规范化，表面拷贝工具一个都不管

把一个产物（一段行为 / 一条记录 / 一个动作 / 一个对象）从**主体 A** 复制到**主体 B**（不同实体 / schema / 坐标系 / 命名空间），用一个「拷贝表面」的工具搬过去：产物**表面在**（结构合法、能加载、能跑），却**不生效 / 部分生效 / 行为怪**。原因——产物的「表面」之外挂着一条**依赖链**，跨主体时每一环都断，而表面拷贝工具**一环都不处理**：

1. **下游表（被产物里的 id 引用的）**：产物里的事件 / 字段引用一些 id（规则 / 子单元 / 结构 / 参数），这些 id 在 A 的下游表有定义、在 B 没有 → 引用悬空、无效果。**修：在 B 按其 id 规约重建这些下游行**，不是改产物表面。
2. **成员归属（模式 16）**：产物要在 B 的「被 runtime 迭代的集合」里登记才被处理；A 拷过来的可能没进 B 的集合（或归属信息没随表面拷贝过来）→ 静默跳过。**修：在 B 重新登记**。
3. **载荷里对源主体的回指（最隐蔽）**：产物的结构 / 二进制**载荷内部**嵌了**指向 A 自己的字段**（A 的实体 id / A 的内部引用）。你只 patch 了那个显眼的「主 id」字段，载荷里**其余嵌着 A-引用的字段原样带过来** → 在 B 上这些引用无效 / 指向错对象 → 失效。**修：把载荷规范化成 B 上一个 working 同类的形态**（拿它的载荷当模板，只保留你**有意**设的字段、其余清成 baseline 值），不是只改主 id。（这是模式 9 的「载荷内部版」：9 是多带一个**外部 sidecar**、删掉即可；本条是载荷**内部**多带源主体嵌入引用、要**规范化**。）
4. **空间 / 相对锚点跨坐标系失效**：产物里的位置 / 锚点 / 下标是**相对 A 的坐标系 / 层级树 / 索引空间**的；同一个 id 在 B 的坐标系里**解析到完全不同的位置**（甚至原点 / 空 / 别的对象）——**id 存在 ≠ 语义相同**（运行时上下文层 ID 相对性 + top-down 模式 DD）。「照搬源的尺寸 / 锚点」会在锚点这环失效：尺寸 / 数值能搬，**锚点 id 必须按语义重映射到 B-valid 的那个**（按语义角色 / 用途配对，不是按 id 数字）。**修：锚点用 B-valid 按语义配；数值（尺寸 / 权重系数 / 倍率）可从源照搬**。

诊断指纹：「我用搬运工具整个搬过来了、表面都在、却不生效 / 怪」。逐环查：① 它引用的 id 在 B 的下游表有吗？② 它进 B 的迭代集合了吗？③ 载荷里有没有嵌着源主体的回指（拿 B 的 working 载荷逐字段比、找你没动却 ≠ baseline 的字段）？④ 锚点在 B 上解析到的是不是同一语义位置（dump B 的锚点表确认）？**表面拷贝工具默认这四环一个都没做** —— 把这四环做成搬运 pipeline 的标准后处理 + 出厂自检每环。

跟模式 9 / 16 / 17 / 19 的关系：它们各是这条链的**一环**（9=载荷外多带 / 16=没登记 / 17=副本漂移 / 19=登记由黑盒管）；本模式是**「跨主体搬运」这个动作会同时触发其中多环**的合成——别修完一环就以为搬完，跨主体搬运默认要过完整条链。诊断纪律见 top-down 模式 W / BB（拿 working 载荷逐字段比，别按「应该长啥样」猜）。

### 模式 22：检测一个「叠加 / 附加层」事件，要读对字段 —— 主状态字段常不随它变、信号落在另一个次级字段

你要在 runtime 检测某事件发生（用来触发后续 / 计数 / 同步），盯着那个「最显眼的状态字段」（主状态 / 当前动作 / 顶层 id），它**一直不变**，于是判「事件没发生 / 检测不到」。但那个事件是**叠加在当前状态之上的附加层**（overlay / additive / 反应层），主状态字段**按设计不反映它** —— 它落在**另一个次级字段**（子状态 / 附加层 id / 模块内部字段）。

- 诊断：「我盯的字段没动、但事件明明发生了」→ 别下「检测不到 / 不支持」，先**枚举这个对象所有可读的状态字段**，在事件发生那刻看**哪个字段跳变了**。主字段稳定 + 某次级字段跳变 = 信号在次级字段。
- 修：检测改读那个**真正反映事件的字段**（次级 / overlay 层），不是主状态字段。挑信号字段时还要**收窄到真正对应目标事件的那一类取值**：若用一个过宽的范围去匹配，别的上下文（移动 / 过渡）也会落进来 → 误触发；每个纳入的取值都要**实测确认只在目标事件时出现**（呼应 top-down 模式 S：从 working 提判别物、别凭「应该是这个范围」拍）。
- 关系：是模式 20（一层多条平行通道、工具只 surface 一种）在「运行时状态字段」上的形态 —— 「当前主状态」和「叠加事件」是两条平行通道，盯主通道会漏掉叠加通道。

### 模式 23：在系统管理的瞬态态里施加的状态不留存（态结束被清）→ 消费方读不到；修 = 窗口内持续补施加 / 态结束后再施加

你在某个**系统管理的瞬态态**（重试中 / 降级中 / 过渡中 / 处理中）进行时**施加一个标志 / 效果**，期望它之后还在；但那个瞬态态**结束时把它清了**（或施加在该态期间根本没「黏住」）→ 之后消费它的逻辑读到「不存在」→ 行为不触发。表象很迷惑：施加调用**成功返回**、时序也对（施加在消费之前），消费方却读不到。

- 诊断：「施加成功 + 时序对（施加早于消费）、消费方仍读不到」→ 怀疑施加发生在一个**会清状态的瞬态态内**。对比**成功**与**失败**两次施加时**所处的态**：失败的常落在瞬态反应态里、成功的落在该态结束后的稳定态。
- 修：① **窗口内持续补施加**（每 tick 重施加，保证瞬态态结束后还有一次落在稳定态）；或 ② **延到瞬态态结束后再施加**（检测该态的下降沿再施加）。别只施加一次。
- 跟模式 10 对照：10 是「你想**清**、框架每个周期重**设**」（清不赢）；本模式反向 —— 「你想**设**、瞬态态把它**清**掉」（设不住）。两者都因为**真正管这个状态的是系统的每周期 / 每态逻辑**，要顺着它的节奏来（持续补 / 挑对时刻施加），不是一次性硬来。

### 模式 24：两个上下文在观察点状态几乎全等、只差一个被填充的子块 → 穷举 dump 全字段 + A/B 频率 diff 定位判别信号

你要找一个**判别控制点**：让某机制只在「该触发」的上下文响应、「不该触发」的上下文不响应。但这两个上下文在你观察的那一刻，**主状态字段几乎全等**（同一个状态 / 同一个流程 / 同一个主 id）—— 光看主字段、甚至看模式 22 那种「哪个字段跳变」都分不出，因为两边表面同形。真正的差别藏在一个**只在一侧被填充的次级子块**里（某个关联对象 / 子事件 / 来源信息的载荷）。

定位手法（比模式 22 更进一步的「怎么把那个判别字段找出来」）：

- **穷举 dump 那个运行时结构的全部字段**（不是只读你想到的几个），在两个上下文**各采多个样本**（不是各一次）。
- 做 **A/B 频率 diff**：对每个字段统计「在 A 的样本里非零 / 出现的比例」vs「在 B 里的比例」，挑出**A 里 100%、B 里 0%**（或反之）的字段 = 判别信号。常见是**一整块相邻字段同时只在一侧被填充**（某子结构的载荷）—— 取其中一个稳定字段当 gate。
- **判据要 100% / 0% 干净劈开**、不是「大部分时候不同」（后者是噪声、会假阳性）；样本每个上下文 ≥ 若干次；两个上下文**单变量**（只差「该不该触发」这一个意图、其余尽量同）。
- 跟模式 22 的关系：22 说「信号在另一个次级字段、枚举字段看哪个跳变」（单上下文、事件发生那刻）；本模式是**两上下文表面全等**时的版本 —— 不是看「跳变」、是看「**只在一侧出现**」，靠 A/B 频率 diff 而非单次跳变。跟 top-down 模式 S（从 working 集提判别谓词）的关系：S 提**共性**（working 们都有什么）、本模式提**差异项**（A 有 B 无），是 S 的「字段级、频率统计」实现。配 top-down 模式 CC（failing 静态全等 working → 转运行时观测）：本模式就是那个「运行时观测」怎么做出判别信号的具体配方。

### 模式 25：路由 / 身份全对但产物错 → 缺陷在叶子资产的**字节内容**、决定性发现工具 = 每个产出单元逐一 byte-hash 对 baseline

一个产物「加载 / 引用对了、状态 / 路由 / 身份标识都正确、可运行时表现就是错的」时，缺陷常在**叶子资产的内容本身**：产物按名字 / id 指向某个资源槽、但那个槽里的**字节被换成了错的东西**（尤其常见于**批量转换 / 跨主体搬运的输出把不该动的 sibling 槽一起覆盖了**—— 见模式 21）。身份级检查（名字对不对、在不在集合里、路由到没到）永远照不出「名字对、内容错」。

- **决定性发现工具（纯离线、零成本）= 把产物的每一个叶子单元，对它的 known-good baseline 同名单元逐一 byte-hash diff。** 不是抽查一两个（模式 F）—— 枚举**全部**单元。差异的那些就是被污染的；更强的指纹：**某个产出单元的 hash == 另一个单元的 hash**（本该不同的两个槽字节相同）→ 坐实「被同一个错误源覆盖」（overwrite 型污染的铁证）。
- 这把「盯着运行时反复猜为什么表现错」换成「一张 hash 表一眼看出哪个槽被换了、被换成了谁」。跟 top-down 模式 U/BB（unchanged-input 字节恒等）同源，但那里是**验证**「我没改的东西没变」，这里是**发现**「哪个我以为没碰的东西被污染了」—— 同一把尺子，一个验、一个查。
- 配套纪律：任何**批量转换 / 重建 / 跨主体搬运**工具，出厂自检里加一条「产物每个单元 vs baseline diff、只允许有意改动的那几个单元不同」（模式 18 三层核对的资产层版本）。overwrite-sibling 是这类工具的高发静默故障。
- 别信「那个资源是 orphan / 没用到」的既有标注就跳过它（模式 15/M）：一个被判「不用」的共享资产可能其实**正被某条路径加载**，它被污染就照样出问题 —— 判「没用」要有运行时证据、不是文档一句话。

## 落地

- 用本 skill 时，先把上面三层映射到你**当前**产物的具体形态（核心资产是什么、sidecar 是什么、
  运行时上下文是什么），列成检查表，再 diff。
- 每条具体结论标明是「观测」还是「推论」（top-down 规则 7），推论先交叉验证再当 modifying 前提。
- 会后若发现某条新模式跨领域成立，抽象成领域中立的一条加进「可复用控制点模式」；只暴露**模式**、
  不暴露**是哪个项目的什么东西**。
