# Top-Down Debugging

> **本 skill 只放抽象逻辑与方法论、零具体项目内容。** 任何具体领域的形态（调试 / 排障 / 构建 /
> 数据转换 等）都抽象成领域中立的模式、放在 `missing-control-points`。这条
> 边界靠下面整篇严格维持 —— 看到下文出现任何**具体项目 / 产品 / 技术栈的术语、标识符、
> 路径、偏移**，那是 bug、应删或抽象掉。

## 何时触发

满足任一条就触发：

- 用户指出「你在打转」「一直试错」「越改越乱」
- 你已经连续做了 2 次同层 probe，信号仍然不收敛
- 症状越来越多，但控制层级还没画出来
- 你开始反复改局部参数 / 入口 / 触发条件 / 配置项（"再换一个值再试"）
- 已经存在可信 handoff、working 样本、设计文档、运行日志、或别人的层级分析，但你还没把它提升成主模型
- 问题还没形成结构，你却已经开始实现或打补丁

触发后先对用户说一句：

`我在用 top-down-debugging，先重画层级，再决定下一轮实验。`

## 目标

先回答这句话：

`working 比 failing，多了哪个控制点，少了哪个错误控制点，或者哪一层根本走错了。`

不要先回答：

- 「再试一个参数」
- 「再换一个入口」
- 「再补一个临时 patch」

## 核心规则

### 1. 先接管可信层级

如果已经有可信来源把问题层级写清楚了，先把它当主模型，不要把它当背景阅读。

可信来源包括：

- working 样本、baseline、线上正常版本
- 可靠 handoff 或复盘
- 已验证的 pipeline 文档
- 可复现的日志、记录、截图、录屏、指标
- 已经跑通的工具链说明

你必须先把那套层级改写成当前任务的检查表，再决定实验。

### 2. 强制四方对照

开始前至少明确 4 个对象：

1. `working`：已知正确或更接近正确的版本 —— 必须是**已验证**正确，不是假设正确。
   特别地，当 `failing` 是「我改动之后的版本」时，`working` = 改动前 baseline，且
   你必须在**同一个出故障的场景 / 上下文**里确认它真的正常，不能默认 baseline 没问题
2. `failing`：当前失败版本
3. `reference`：源输入、协议、规格、源数据、目标行为或外部标准
4. `layer model`：当前采用的控制层级图

缺任何一个，都先补，不要继续局部修补。

### 3. 先找层，再找点，再找值

调试顺序固定为：

1. 哪一层出了问题
2. 这一层缺了哪个控制点
3. 这个控制点里的哪个值不对

不要跳过前两步直接调值。

### 4. 每轮实验只回答一个问题

好实验必须是单变量的，并且写清：

- 这轮要证伪什么
- 改的是哪一层
- 不碰哪几层
- 成功和失败分别意味着什么

如果一轮实验同时改了两层以上，这轮结果默认不干净。

### 5. 两次负信号后强制升层

同一层连续两次负信号后，必须停止在该层硬试，回到上一层重画控制图。

不要出现：「再换一个值 / 入口 / 配置 / 开关试试」，除非你先说明：上一层为何已经被证伪。

### 6. 已知失效方向直接禁用

如果可信来源已经证明某类方法 / 方向在当前问题里**根本不会产生有效结果**，就不要继续
在这类方法内部微调参数。「不会产生有效结果」在具体领域里的形态各异（不会触发 / 不会被
路由 / 不会被加载 / 不会响应 / 静默失败 / 命中后无反馈 等），抽象后是同一类「方向已被
证伪」信号。

正确动作：

- 把「方向选择错误」记为当前结论
- 升层到「正确方向是什么」
- 下一轮实验只验证新方向，不再回头修旧方向

**但「已知失效」本身也是一个结论，必须能追溯到已验证的根因。** 一个「死路」如果只来自
单次失败实验、没有 root-cause 清楚「为什么失败」，它可能是误判 —— 失败的真因也许是
工具 bug、参数 / 构造错误、查询层级错误、上下文条件不匹配，而不是这条路本身不通。
拿到新工具 / 新理解后，重新审视一个旧「死路」标记是合理的，不算回头。

具体领域的失效形态例 → `missing-control-points` 案例段。

### 7. 观测与推论分离，推论不能直接当实验前提

把信息分成两类：

- **观测**：工具 / 系统 / 协议直接产出的**可被独立读取**的事实
- **推论**：对观测的**解释**（"因为 X 所以 Y"、"这说明 Z"、"那应该是因为 W"）

推论**不能**直接当下一个实验的前提。一个推论要升级成可用的前提，必须先：

- 用 observer / 只读手段把它**降级成观测事实**，或
- **交叉验证** —— 用 ≥2 个独立角度 / 方法得出同一结论

每个实验前先写一张「依赖前提清单」，列出本实验假设哪些前提为真、每个前提的验证状态
（已验证观测 / 待验证推论 / **已被实验推翻=作废**）。清单里只要有未验证的推论，就先去
验证那个推论，不要做实验。实验失败时，**先逐个回头查前提是不是错的**，再怀疑实验本身。
被推翻的结论要**显式标作废、不删除**（留作「此路不通」的记录、防同一死路反复重走），且
**作废结论不得再当任何后续实验的前提**——否则它会悄悄在台账里复活、整条决策链建在错前提上。

**observer 优先于 modifying。** observer 实验（只读、不改变被观测对象的状态）错了
只是多一轮；modifying 实验（改状态、写内存、动配置、发请求改远端）基于错推论会引入
副作用 / 脏状态 / 不可逆破坏 / 误导性结果。能用 observer 验证的，绝不先做 modifying；
modifying 实验的前提必须全部是已验证观测。

具体领域的观测手段例 → `missing-control-points` 案例段。

### 8. 真因 narrative 闭环验证是 modifying 实验的前提

一轮 modifying 实验「执行成功但目标没达成」时，**不要在 modifying 这一层 iterate**（换
参数、调时机、加另一个 patch、再换一种实施方式）。要先检验当前 narrative 是否能解释
为什么这次 modifying 跑了但没用。不能解释 = narrative 没闭环 = 不能基于它继续 modify。

**三方闭环检验**：

- **working** 为什么 working — narrative 能给一个具体机制
- **failing** 为什么 failing — narrative 能给具体的失败 gate
- **上次 modifying 跑了为什么没用** — narrative 能解释为什么这次 patch 没击中失败 gate

任一不能解释 = narrative 没闭环。强制：暂停 modifying、回头补观测 / 读源 / 分析，把
缺的那一环补上、闭环了再设计下一个 modifying。

跟规则 7（观测/推论分离）的区别：规则 7 防的是「单个推论没验证就当前提」；规则 8 防的是
「多个推论拼出的 narrative 没解释所有现象就当 modifying 设计依据」。每条推论单独都
"看似有理"、**全凑起来缺一环**也不能 modify。

跟规则 5（两次负信号升层）的区别：规则 5 是同层 probe 失败要升层；规则 8 是 modifying
执行成功但目标没达成要回头闭环 narrative —— 补上「为什么 modifying 没用」这一环、然后
才能继续。

闭环验证后的 next-step 通常长这样：
- 「我之前推的 narrative 缺解释 X，现在补上 X = Y，narrative 闭环 ✓」
- 「基于完整 narrative，下一个 modifying 应该攻 Z 层，不是上次的 W 层」
- 「在 modifying 之前先用 observer 抓 Z 层数据，per 规则 7 cross-validate Z 是失败 gate」

## 通用控制层级模板

不是每个问题都要用全套，但至少要明确你当前在第几层：

1. **目标行为层** — 用户真正想看到什么
2. **运行时表现层** — 现在实际发生了什么
3. **路由/触发层** — 是谁把这条链路启动起来的
4. **主资产层** — 核心代码、数据、模型、配置主体
5. **sidecar / 元数据层** — 附属事件、辅助资源、校验、时序、映射表、缓存、索引、标签、权限
6. **运行时上下文层** — 场景、角色、网络状态、权限、平台、资源包、环境变量
7. **外部依赖层** — 工具链、打包器、格式转换器、服务、驱动、第三方库

## 每层必须问的问题

对每一层都问：

- `working` 有什么而 `failing` 没有
- 是「值不对」，还是「根本没传到这层」
- 是「主资产有问题」，还是「sidecar 残留」
- 是「文件 / 配置就错了」，还是「运行时上下文改写了结果」
- 这一层的结论来自证据，还是来自猜测

## 最小差异表

继续修改前，先产出最小差异表，至少包含：

- `working / failing / reference / layer model`
- 当前比较的是哪一层
- 本层最关键的 1-5 个控制点
- 发现的差异：缺失、错位、残留、越层、上下文依赖
- 下一轮实验要证伪的问题

## 常见打转模式

### 模式 A：把可信层级当背景材料

症状：

- 已有文档明说问题在某层，你还在下一层微调
- working 样本已经证明某条路不成立，你还在重复局部 probe

处理：

- 先把文档里的层级提升成当前主模型
- 用主模型重新标记当前实验所在层

### 模式 B：把 sidecar 问题误判成主资产问题

症状：

- 主体代码、数据或流程是对的
- 但**附属层**（辅助事件 / 校验 / 时序 / 缓存 / 权限 / 元数据 / 附件 等）不对

处理：

- 冻结主体
- 只查 sidecar 与上下文层

### 模式 C：把上下文问题误判成文件问题

症状：

- 同一份文件 / 数据在不同运行时上下文（不同场景 / 角色 / 网络状态 / 权限）里表现不一样
- 只改文件内容、忽略「是不是被上下文改写了」

处理：

- 把「上下文」单独拉成一层
- 不要继续只改文件内容

### 模式 D：同层反复探针

症状：

- 换 payload、阈值、入口、时机，结果只是换一种错法

处理：

- 两次负信号后强制升层
- 回答「为什么这一层值得继续调」

### 模式 E：研究问题直接开始实现

症状：

- 还没弄清控制图就开始写代码、改配置、跑实验
- 结果产出越来越多，但问题空间没有缩小

处理：

- 先补 `working / failing / reference / layer model`
- 先做差异表，再决定实现顺序

### 模式 F：抽查一层就宣布它无罪，然后过早升层

症状：

- 对某层只试了几个字段 / 参数 / 条目，没命中，就校验「不是这层」，升层到更深或更底层
- 在深层耗很久，甚至引入新故障
- 最后发现答案就在那层**没查完**的字段里

处理：

- 一层要判「无罪」，必须对它做**完整对比**：全字段 / 全条目 diff，对着干净参照
  （原始基线 / working baseline / 模板）
- 从模板 clone 来的数据会带着模板的**全部**属性；你只清掉想到的几个字段，剩下的还在
- 升层的前提是下层被「完整排除」，不是「抽查排除」。「试了几个值没用」≠「这层无罪」

### 模式 G：这一层全绿了，目标还是没达成

症状：

- 某层自己的成功判据全部满足（调用全返回 OK、值全部正确、检查全过）
- 但用户要的最终结果仍然没出现

处理：

- 这一层是「正确但不充分」 —— 缺失的控制点在一个你**还没建模**的层
- 不要继续打磨这个全绿的层（再调一个参数、再换一个调用都是浪费）
- 立刻升层：补全控制图，找「全绿层」之外还有谁参与了目标行为

### 模式 H：推论链滚雪球

症状：

- 单次实验 → 立刻给一个推论 → 基于这个推论直接设计下一个实验 → 再给一个推论……
- 推论一个叠一个，中间没有一个被独立验证或交叉验证过
- 走了很多轮之后，发现最底下那个根推论就是错的，上面全塌
- 同一个根推论被推翻好几次，每次只换一个表层解释，没回到「这个推论本身没验证过」

处理：

- 每条结论标明：是「观测」还是「推论」，证据强度是单次 / 多次 / 交叉验证（见规则 7）
- 推论当实验前提前，先降级成观测或交叉验证
- 一串实验如果共享同一个未验证的根推论，它们撞同样的墙**不是「反复验证」**，是同一个
  错误的多次表现（同模式 D，但根因在「推论」不在「层」）
- 真正能打破推论链的实验，往往是换一个**独立的观测角度**去直接验根推论，不是在原链上再加一环

### 模式 I：用户提出方法论质疑时只辩护不改流程

症状：

- 用户说「你的推论有没有验证过」「会不会在错的前提上越走越深」「你需要一个流程」
- 你回答「我觉得这次没问题」「前面验证过了」，继续按原节奏做实验

处理：

- 用户的方法论质疑**优先级高于当前实验** —— 先停下来，把当前所有 active 结论列成
  台账（每条标观测 / 推论 + 验证状态），自己 audit 一遍
- 把质疑落地成**显式流程**（规则 7 的「依赖前提清单」就是一种），写进 skill 或项目
  文档，让后续不再依赖临场记得
- 这种质疑通常是对的 —— 用户能从外部看到你在打转，而你在链条里看不到

### 模式 J：把「改动后出现的故障」默认归因给改动

症状：

- 你做了改动，之后在某个场景第一次见到故障
- 你默认「故障出现在改动之后 ⇒ 改动导致故障」，直接开始在改动内部找因
- 连续几轮换实现、换参数、换假设，每轮重建 + 复现 + 改假设，信号不收敛
- 从没验证过：改动前的 baseline 在**同一个出故障的场景**里是不是本来就故障

处理：

- 「故障出现在改动之后」≠「改动导致故障」。这是 post hoc 谬误，本质是 `working`
  对照组从未被真正验证 —— 你的 `working`（改动前 baseline）是**假设**正确，不是
  **已知**正确。改动前你可能根本没在这个场景跑过 baseline
- 见到改动后的新故障，第一个 control 实验永远是：回滚到改动前 baseline，在**同一个
  出故障的场景 / 上下文**里复现。baseline 也故障 ⇒ 故障预存在、与改动无关，立即停止
  在改动里找因，升层到「这个预存在故障在哪一层」；baseline 正常 ⇒ 才轮到查改动
- 这个 control 通常极便宜（回滚 + 同场景重试一次），却能一步锁定 / 排除整条方向。
  跳过它就是在未验证前提上滚雪球（见模式 H），代价是多轮误判 + 多次破坏性复现
- 用户说「会不会跟你的改动无关」「为什么是 X 导致的」时，这条质疑通常就是在指这个缺失
  的 control —— 立刻去补 baseline-in-same-context 实验，别辩护（见模式 I）

具体形态（领域中立）见 `missing-control-points` 的「可复用控制点模式」。

### 模式 K：modifying 跑通但目标没达成、就继续 iterate modifying

症状：

- 你做了一轮 modifying（写状态 / 改配置 / patch 字段 / 调用接口 / 加拦截层 / 等等）
- modifying 自己的成功判据全部满足：触发了、返回 OK、写入值能读回、所有内部 check 都过
- 但用户能感知的最终目标**没达成**（输出没出来、UI 没改变、状态没切换、行为没变）
- 你的反应是 iterate modifying：换参数、调时机、再多 patch 一个字段、再调一个接口、再加一层拦截
- 连续 2-3 轮 modifying iterate、每轮 modifying 自己都成功执行、但目标都没达成

处理：

- 这跟模式 G 不同：模式 G 是 read / observer 维度「全绿不达标」、要升层补建模；
  模式 K 是 **modifying 维度全绿不达标**、要先确认真因 narrative 是否闭环（见规则 8）。
  modifying 跑通但目标没达成 几乎一定 narrative 缺一环。
- **暂停 modifying**，做三方闭环检验：narrative 能否解释 working / failing / 上次 modifying？
  任一不能 = narrative 没闭环 = 不能基于它继续 modify。
- 没闭环时下一步必然是 observer / 读源 / 分析 补缺环，不是再调一版 modifying。
- 跟模式 H 区别：模式 H 防 hypothesis chain 滚雪球（单线推论叠加）；模式 K 防 **modifying
  chain 滚雪球**（多次实施都没效但每次都 fire），后者更隐蔽 —— 因为「每次都成功执行」
  会假装是修复 partial progress，实际是 narrative-blind iteration。

具体形态（领域中立）见 `missing-control-points` 的「可复用控制点模式」。

### 模式 L：多个指标同步累积到同一数字 → 误归因为 causation

症状：

- 观测里看到指标 A 和指标 B **每个采样点都 1:1 相等**（A=135 时 B=135、A=375 时 B=375）
- 直觉归因「A 触发 B」或「A 和 B 是同一条因果链的两侧」
- 据此设计实验：disable A 应该让 B 不再累积
- 实验结果：disable A 后 B 仍累积到同一数字 → 1:1 是 **coincidence**、不是 causation
- A 和 B 各自独立累积到同一 ceiling、可能因为它们都受同一个**上游 cause** 影响（cause ≠ 指标）

处理：

- 多指标同步累积到同一 ceiling、第一假设是「都受同一上游 cause 影响」、而不是「A 触发 B」
- 验证方式 = **disable 对照实验**：能 disable 其中一个指标的 source、观察另一个是否仍累积
  到同一数字。如果是 → 1:1 是 coincidence、真因在更上游
- 这是模式 H（推论链滚雪球）的具体表现 —— 但更隐蔽，因为「1:1 相等」看起来像强证据
- 配合规则 7：每个指标的「causation」解释都是**推论**、不是观测；必须 disable 对照验证才能升级为观测

### 模式 M：「推论级 close」也可能错、不是永久 settled

症状：

- 之前某轮调查得出结论「真因是 X、close」并标了「推论级、未直接验证、未来可推翻」
- 后续接手 task 时把这个 close 当 settled 前提、不再质疑
- 基于这个推论级 close 排出「哪些方向不值得查」的优先级、绕开了正确路径
- 后期实测推翻这个 close → 整个「绕开」决策链失效

处理：

- 「推论级 close」标签**隐含**「未来可推翻」、不是 settled。每次接手 / restart 调查时，
  先重新审视推论级 close 是否仍站得住
- 推论级 close 跟「证明级 settled」的区别要严格保持：证明级 = 多角度 cross-validate
  实测、推论级 = 单角度推导 + 缺乏直接 verify means
- 如果推论级 close 排除了某 path、但后续 N 轮实验都撞墙、**重新启用那条 path 做直接
  verify 实验**比继续在已 explored path 内微调更高 leverage
- 「推论级 close」本质是「暂停调查的理由」、不是「调查结论」。当 cost-benefit 变化（新工具、
  新理解、或后续路径失败累积）就该 reopen

### 模式 N：多轮 modifying-verify 循环（模式 K 的极致表现、cost 已很贵）

症状：

- 模式 K 的升级版：不止 modifying 跑通目标没达成、而是**连续 N 轮** modifying + verify +
  推翻、再做下一个 modifying（每轮各自 cost 高 —— 重建 / 部署 / 重启 / 用户实测 等）
- 每轮 verify 都揭示新 finding、又 pivot narrative、又 spawn 下一个 modifying
- N+ 轮之后用户介入：「停下来多做离线分析、你每次重启都能出 bug」
- 真因实际不在 modifying 路径、是**更深层结构信息缺失**（需要离线深挖才能定位）

处理：

- **硬 limit**：连续若干轮 modifying 都 verify 推翻、强制 **暂停 modifying-verify 循环、
  做一段离线深挖**（读源 / 反推数据结构 / 走调用链 / 看上游 / 看相邻系统的实现）。
  「若干」由 cost 决定：单轮 cost 越高、limit 越低
- 跟规则 8 / 模式 K 的区别：规则 8 + 模式 K 是 single 轮失败要 narrative 闭环；模式 N 是
  **multi-轮**连续失败需要**跳出 modifying 框架** —— 可能根本 fix 不在原来 modifying 的
  位置、而在更深的结构 / 协议 / 状态机里
- **离线深挖 vs modifying 迭代**的 leverage 通常差一个量级 —— 当 modifying 单轮 cost
  显著高于离线深挖单轮 cost（典型阈值：1 modifying = 1 user session、1 离线深挖 = 1-2 小时
  独立工作）、连续失败 N 轮就该 pivot
- 用户介入要求深挖底层的信号（「你每次重启都出 bug」、「你得多离线分析」）是模式 N
  触发的典型外部 trigger —— 不要辩护、直接 pivot 到离线深挖
- 每轮 modifying-verify 记 build 系谱：「本轮推翻了什么 narrative + 新 narrative 假设 +
  下轮验证什么」。如果一眼能看出「narrative 在 N 轮之间反转过 N 次」、立刻 pivot

具体形态（离线深挖突破 vs modifying loop 的 leverage 对比）见 `missing-control-points` 模式 5。

### 模式 O：修一个实例、漏掉它的孪生控制点

症状：

- 你识别出一个 pattern 的问题（某类调用在热路径上阻塞 / 某类入口缺 gate / 某类状态没清），
  在**一个**点上修好、验证通过
- 一段时间后同样的症状从**另一个点**再冒出来 —— 同一个 pattern 的孪生实例在别处也存在、当初没一起修
- 「上次不是修过这个吗」的困惑

处理：

- 一个 pattern 的 fix 默认是**不完整**的、除非你确认没有第二个同类点。修完一个实例、立刻用
  结构搜索（grep / 调用图 / 同名 helper 的所有 call site）**枚举这个 pattern 的所有孪生**
- 典型孪生形态：成对的 init/teardown、主路径 + 慢路径都各调一次同一个昂贵操作、一个 helper 被
  多处调用但只有一处加了保护、startup 路径和 steady-state 路径各有一份相同逻辑
- 「把昂贵 / 阻塞操作挪出热路径」「给入口加保护 gate」「清理残留状态」这三类 fix 最容易留孪生 ——
  因为它们针对的是一个**反复出现的 pattern**、而 pattern 通常出现不止一次
- 这跟模式 F（抽查一层就宣布无罪）相邻：F 是「一层没查完」、O 是「一个 pattern 没修完」

### 模式 P：failing 是间歇的、却用单次结果下结论

症状：

- failing 不是每次都复现 —— 同样操作有时触发、有时不触发
- 你做了一版 fix、跑一次没复现、就宣布「修好了」
- 或者：你抓到一次复现、把那一次里**碰巧同时出现**的现象当成 failing 的 correlate / cause
- 后来 failing 又出现（fix 没真修）、或那个「correlate」在别的复现里根本不在场

处理：

- failing 间歇时，**单次 non-repro ≠ 修好、单次 repro 的伴随现象 ≠ correlate**。两个方向都要警惕
- non-repro 只是「这次没踩中触发条件」、是 **inconclusive 不是 success**。要么找到确定性触发条件、
  要么让 instrumentation 常驻、**等下一次自然复现时带着观测**再判断
- 单次 repro 里和 failing 同时出现的东西、可能只是**当时上下文的巧合**（例：你恰好在某状态下复现、
  那个状态的伴随信号被误当成 failing 的特征）。需要 ≥2 次独立复现、看伴随现象是否稳定共现（呼应规则 7 交叉验证）
- 间歇 failing 的正确姿势：**先投资可常驻的低成本观测**（计数器 / 日志、不改行为）、然后在多次
  自然复现里收集、而不是靠「改一版→测一次→看复现没」的高成本循环（那会撞模式 N）

### 模式 Q：观测字段本身是条件填充的默认值、伪装成测量

症状：

- 你读一个观测工具自己产出的字段（日志值 / trace 列 / 面板读数）、当成「观测事实」直接对照
- 在 `working` 上下文它是某个值、在 `failing` 上下文是另一个值 —— 你据此判断「这就是差异」
- 实际上这个字段**只在某些条件下才真正被采集 / 计算**、其他条件下显示的是**默认值 / 上次的残值 /
  跳过采集后的占位**、看起来像数据其实不是

处理：

- 规则 7 区分「观测 vs 推论」、模式 Q 是更隐蔽的一层：**观测工具自己的输出也可能不可信** —— 一个
  字段在日志里有个数、不等于它在这个上下文里被真正测过
- 把一个工具字段当跨上下文对照前、先确认它在**两个上下文里是同样口径采集的**：是不是有
  `if 条件 { 才计算这个字段 }`？两个上下文是否都满足那个条件？不满足的那个显示的是默认值吗？
- 验证方式：读产出这个字段的**源**（采集代码 / 公式 / 取数逻辑）、确认它在 failing 上下文确实执行了
  采集。源不可读时、用一个**已知该字段必然非默认**的对照样本去标定
- 这是「apples-to-oranges 对照」的一种 —— 两个上下文的同名字段语义不同（一个是真测量、一个是默认占位）、
  diff 出来的差异是 artifact 不是信号。配合规则 5：基于 artifact 的「差异」继续深挖 = 在错误信号上打转

### 模式 R：在特权 / 开发环境里测通过、误当成「已验证」

症状：

- 你在**自己的开发环境**里测一个产物（构建、配置、部署包、脚本）、通过了、宣布「验证 OK」
- 但这个产物里有一个**隐式依赖当前环境**的假设（硬编码的绝对路径 / 本机才有的依赖 / 特定目录布局 /
  特定区域设置 / 已经装好的前置）
- 开发环境**恰好满足**那个假设（所以测通过）、换一个环境就失败
- 别人 / 别的机器 / 干净环境拿到后用不了、而你的测试从没覆盖到那个差异

处理：

- 「在我的环境测通过」≠「验证了」—— 开发环境往往是**特权特例**：它满足了一堆你没意识到的隐式前提。
  这跟模式 J 互补：J 是「working baseline 没在 failing 场景验」；R 是「pass 的那次测试本身在一个
  privileged 环境、没在目标环境验」
- 交付 / 发布 / 跨环境复用前，**显式列出产物对环境的假设**：路径是绝对还是相对？依赖的东西目标环境
  有没有？区域 / 编码 / 权限 / 目录结构是否一致？每条假设问「在我的机器之外还成立吗」
- 暴露环境耦合的方式：要么**在一个真正不同的环境测**（干净机 / 别的路径 / 别的 locale）、要么
  **静态审产物**找写死的环境特征（grep 绝对路径 / 机器名 / 盘符 / 本机专属常量）
- 「能跑」有两种：在**任何合规环境**能跑、vs 只在**我的环境**能跑。后者是未验证的伪通过

### 模式 S：信任候选的「既有分类」、而不从 working 集提判别谓词

症状：

- 你在一个**大候选空间**里选实例（入口 / slot / 配置 / 资源 / 字段）给某机制用
- 你信任一份**既有的候选分类**（文档 / 记忆 / 别人的标注说「这个是 X 类、那个是 Y 类」）去选、
  选了基于分类「应该可用」的候选
- 实测不可用 —— 而**另一个同机制的实例却可用**
- 事后发现：那份分类是没验证的推论（模式 M）；多个 working 实例其实**共享一个可提取的判别属性**、
  你没从它们身上提取、而是信了分类标签

处理：

- 候选的「既有分类」是推论（模式 M），**不是判别谓词**。真正的判别谓词要从 **confirmed-working 的实例
  集**里提取 —— 看 N 个（≥2）已证可用的实例**共享什么属性**。尤其优先看它们在**上游路由 / 调度 / 上下文**
  里被怎么对待的属性（谁引用它、从哪个态能进它），而不是实例**自身**的属性 / 别人贴的标签
- 提取出谓词后**先当预测器用**：按谓词选 2-3 个新候选、实测验证谓词。通过 = 谓词可信、可继续按它批量选；
  不通过 = 提取错了属性、回 working 集看还共享什么。**先验证谓词、再批量** —— 别用未验证谓词一次性铺开
- 关键转变：从「比较 working/failing 做**诊断**」升级到「用 working 集的**交集**做**预测**」。working 集
  ≥2 个时、它们的共性比任何单个候选的分类标签都可信
- 跟模式 M 的区别：M 是防守（别把推论级 close / 分类当 settled）；S 是进攻（用 working 集提谓词**替代**
  信任分类）。两者配对：发现分类不可信（M）后、正确的下一步就是 S，而不是逐个试候选（模式 D）

具体形态（从一个大候选空间选实例时，不信既有分类标签、改从 confirmed-working 集提共享判别谓词
做预测）见 `missing-control-points`。

### 模式 T：空/阴性结果来自没验证过能力的探针 → 假阴性

症状：

- 你跑一个 check（grep / 扫描 / 查询 / 测试 / 验证），得到**空 / 阴性**结果（"没找到"、"没泄露"、
  "没命中"、"没复现"），据此宣布「不存在 / 没问题」
- 但你从没确认这个探针**本身能工作 / 真的跑了 / 在已知阳性情况下确实会命中**
- 探针其实**静默失败**了：工具没装 / 命令名错 / 路径错 / 错误被 `2>/dev/null`（`-ErrorAction
  SilentlyContinue`）吞掉 / 权限不足 / 查错了对象 / 跨环境工具缺失 → 输出空、看起来像「干净」

处理：

- 阴性结果**只有探针通过 positive control 后才可信**：先用一个**已知必然命中**的输入验证探针会命中
  （grep 一个你确定存在的串、查一个你确定在的对象），再信它的「没找到」
- 静默失败高发源：工具不在 PATH（`command not found` 被 suppress）、stderr 被重定向吞掉真错、
  查询层级 / namespace 错（在父层查叶子）、跨环境某工具根本没装
- 这是规则 7 的底层延伸：**「探针的输出」本身也要被验证** —— 一个 check 返回空、不等于「目标不存在」、
  可能是「check 根本没正常执行」。换一个**独立、已知可用**的探针复验阴性结论（尤其结论有重大后果时）
- 跟模式 Q 的区别：Q 是探针**有输出、但语义是条件默认占位**；T 是探针**没输出 / 阴性、因为它根本没正常
  运行**。两者都是「别把探针输出当地面真值」、但一个是"假数据"、一个是"假空"

具体形态（某验证用的工具静默缺失 / 报错被吞 → 阴性结果其实是「探针没跑」而非「目标不存在」；
换一个不依赖该工具的独立探针、先过 positive control 再复验）见 `missing-control-points` 模式 2 旁注。

### 模式 U：复用一个「能用」的工具去做它没被验证过的新操作

症状：

- 你复用一个现成工具 / 函数 / 库来做某事。它在**已有用途**上一直没问题（你信任它）。
- 你用它做一个**相邻但不同的操作**（overwrite → insert/add、读 → 写、单个 → 批量、相同尺寸 → 改变尺寸）。
- 结果在下游**崩溃 / 损坏 / 行为异常**，但工具自己「跑通了」（没报错、自己的 round-trip 也过）。
- 你在自己新写的调用代码里反复找因，没意识到**工具内部那条新路径本身从没被任何人跑过**。

处理：

- 「工具在用途 X 上可靠」**不蕴含**「工具在相邻用途 Y 上正确」。同一个工具里，**被反复使用的代码路径**经过了
  实战检验，**没人用过的分支**可能是带 bug 的死代码——尤其是「数量 / 尺寸会变」的操作（add/insert/delete/resize），
  它要重建索引表、偏移、计数，而「同尺寸 overwrite」用途永远不触发这段重建逻辑。
- 复用工具做新操作前，先问：**这个操作在这个工具里被验证过吗？** 查它的既有调用点都在做什么用途（grep 调用），
  若全是用途 X、你是第一个用途 Y，就把工具的 Y 路径当**未验证代码**对待、先单独验证它。
- **验证 serializer / rebuild / round-trip 类函数的决定性离线手段 = unchanged-input 字节恒等**：
  `serialize(parse(x)) == x` 对**未修改**的 x 必须 byte-identical。若连不改都不恒等，函数就是 lossy / 模型错的，
  改了之后只会更错。这个测试**纯离线、零成本**，能在你做任何 modify 实验前就抓出「重建逻辑写错」——
  例：一个容器重建函数对未改输入 byte-identical 失败（输出多出几 KB、某计数字段按错误公式算），
  正是它把容器头写坏、下游崩；而该工具的「同尺寸 overwrite」用途从不触发这段重建、所以一直没暴露。
- 跟模式 N 配对：当 modify-test 很贵（每次要重启 / 复现 / 崩溃）且连续失败，**别再 modify-test**，转去做这种
  unchanged-input 字节恒等 + 结构对照的**纯离线**验证——它一步定位「重建/序列化写错了哪个字段」，比 N 次崩溃测便宜一个量级。
- **research-first 是更前置的省坑**：动手深挖（尤其要改一个不可读的产物 / 啃黑盒 / 自造格式）前，先查社区 / 文档
  是否已解此问题——可信的外部资料是 §1 的「可信层级」之一。例：以为某项要 patch 主程序里的硬编码表、
  正要动手啃底层，先查文档 / 社区发现它其实是个**可外部修改的文本配置**、整条深挖深坑直接绕开。

### 模式 V：绕开难点的 workaround「能跑」≠ 满足真实需求

症状：

- 真正的解法卡在一个难点上（崩溃 / 没通 / 很贵）。你找了个**绕开难点**的 workaround，它**能跑、结果看着对**。
- 你（或顺着惯性）就把 workaround 当交付了。
- 但 workaround 是靠**复用 / 寄生 / 共享**某个已有东西达成的，它**没有满足需求里那条「难点对应的属性」**
  （独立性 / 隔离性 / 可扩展性 / 所有权）——一旦那个被复用的东西变化，workaround 跟着崩。

处理：

- workaround 验收要回到**原始需求的每一条属性**，不能只验「能跑」。问：需求要的是「能运行」还是
  「**独立**地能运行」？workaround 给的是哪个？那个被绕开的难点，往往**正是**需求里最关键属性的来源——
  绕开它 = 没满足那条属性。
- 例：需求是「一个**完全独立**的新实例」，难点是「新建实例会崩」。绕开法 = 复用一个已有实例（不崩、能用），但它和
  原 owner **共用一份、不独立**——owner 一回退它就跟着回退。是旁观者一句「那不还是用原来的东西吗」点破的。
- workaround 可以作**临时证明**（证明链路的其余部分通），但要**明确标注它不是交付**、并把「真正难点」继续列为
  必解项；别让「能跑的临时版」掩盖「真需求未满足」。这跟模式 G（这层全绿但目标没达成）同源：局部成功 ≠ 目标达成。

### 模式 W：用「应该长什么样」的预期去判一个 transform 的输出坏没坏

一个转换/构建/序列化步骤的输出**看着不符合预期形态**时，倾向直接判「失败、产物坏了」。但「预期形态」常来自
文档措辞或直觉、而不是事实。**正确动作：拿那个已知能跑的 baseline 产物，对它的实际形态（字节/结构/容器布局）做对比**；
形态一致就放行，不一致再查。
- 例：某工具打包出的产物、内层是文本形态（非预期的二进制），第一反应是「序列化失败」；一解**那个已知能正常加载的
  baseline 产物**、发现它**也是**同样的文本形态（文档「会序列化回二进制」是 stale 措辞）→ 我的同形产物有效。
- 这是模式 J（同上下文 baseline 对照）从「行为」延伸到「**产物的静态形态**」：判产物坏没坏、不靠「它应该长什么样」、
  靠「已知能跑的那个长什么样」。尤其涉及第三方工具（其文档 / 你的心智模型可能与实际行为不符）时，baseline 的事实 > 文档的描述。

### 模式 X：多个独立源同时存在 → 逐个移除的单变量测试个个阴性 → 误判整层无罪、升错层

症状：

- 怀疑某层（某份数据 / 配置 / 某模块 / 某组事件）是病根。你做**单变量移除**：删 A → 症状还在；删 B → 症状还在。
- 于是判「这层排除」、升到下一层——甚至得出「逐项排除后**剩下只能是 X 层**」的消元结论。
- 但这层其实有**两个（或多个）独立源**，每个都能**单独**造成症状。删 A 时 B 还在 → 症状在；删 B 时 A 还在 → 症状在。
  **逐个删都阴性，恰恰是「多源」的指纹，不是「无罪」的证据。** 单变量移除只在「单一源」假设下才能证伪一层。

处理：

- 怀疑一层、但逐个移除都阴性时，先做**一次性全删**（该层所有候选同时移除）再判：全删后症状消失 = 这层确实是源、
  且不止一个 → 回头**二分**（分组移除）定位具体元凶、并尽量保留无关项；全删仍在 = 这层才真无罪、可升层。
- 更强的交叉校验：**用领域硬不变量约束搜索空间**。当一条一阶逻辑 / 不变量与你的消元结论**直接打架**时，
  先怀疑消元（它最常因「隐藏的多源」或「没隔离的复合变量」而失效），而不是信消元、去验那个不变量本不该成立的层。
- 例：某产物在某段时间表现出一个不该有的属性，怀疑源头在「数据层 A」。test1（中和 A 里的源 X、留源 Y）仍有该属性；
  test2（删源 Y、留源 X）仍有 → 误判「A 层排除、剩更深的 B 层」、并卡在 B 层挖若干轮。真相：X 和 Y 是 A 层里**两个
  独立的源**、各自单独都能造成该属性、分开删各自测不出。同时还有一条硬约束被忽略——一条领域不变量直接推出「该属性
  逻辑上只能在 A 层」、与「剩 B 层」的消元结论直接冲突。决定性测试 = **一次性把 A 层该范围所有候选全删** → 属性消失；
  再分组二分 → 锁定元凶、保留无辜项。教训：分开测的两次阴性 ≠ 排除该层；冲突的硬不变量 > 可疑的消元结论。

### 模式 Y：怀疑「自己引入的子系统」致间歇故障 → 先整体禁掉坐实因果，再拆开二分

症状：

- 一个**自己引入**的复合子系统（多个耦合组件）被怀疑是某个**间歇性**故障（死锁 / 崩溃 / 降级 / 偶发
  错误）的根因
- 你直接去**子系统内部**逐个组件试改、或试图在故障发生后在线关掉它 —— 但故障一旦发生就**无法在线解除**
  （死锁后开关失效 / 状态已不可逆 / 锁已孤立）
- 多个组件耦合，单看任一个都说不清是不是它，逐个改又撞模式 N（贵 modify-loop）

处理（两步，粗到细）：

1. **broad cut（粗因果切分）**：从**启动**就**整体禁掉**整个嫌疑子系统（所有组件一起关），跑到平时故障
   出现的时长。不再故障 = 坐实是这个子系统（**一刀切清「是不是我」**）；仍故障 = 子系统洗清、立即升层去
   别处。⚠️ 必须**从启动就关** —— 间歇故障多在「不可逆点」之后才显形，事后关无法解开已发生的死锁 / 已孤立
   的锁。代价：暂时丢掉该子系统提供的有用功能（这是 broad cut 的已知成本、不是失败）。
2. **split-gate bisect（拆开二分）**：坐实后，把子系统拆成**多个独立的启动期开关**，按先验开「有用但无辜」
   的组件、关「嫌疑」组件。故障消失且有用功能还在 = 锁定精确元凶、**且保住了有用部分** —— 这不是「功能
   换稳定」的取舍，而是定位到具体有害子路径**只关它一个**。选哪个组件先开先关、用**故障指纹**（故障前最后
   一次活动落在哪条代码路径）做先验。

关键：判据始终是一个**客观、与主观体感独立的连续量**（如某心跳计数是否单调推进 vs 冻住），故障 = 它冻住
而其它进度仍推进。靠它客观确认每次实验「故障有没有真消失」，而非「这次没遇到」（间歇故障单次 non-repro
不算数，见模式 P）。

跟模式 N 的关系：模式 N 是「贵 modify-loop 连续失败 → 转离线深挖」；模式 Y 是离线深挖**之后**、已能定位到
「嫌疑落在某个自引入子系统」时的**收口手法** —— 用一次 broad cut 一刀切清因果、再用 split-gate 把「是我的
哪部分」二分出来，比继续在子系统内部逐组件试错快、且天然导向「保住无辜组件」的精准修复。具体形态见
`missing-control-points` 模式 11。

### 模式 Z：测量用错坐标轴 / 单位 → 一个数据层 bug 伪装成深层运行时玄学

症状：

- 你在排查一个「某观测量随某变量演化」的问题，把观测量（位移 / 进度 / 状态 / 计数）对着**你顺手取到的那个轴**
  （外部计数序号 / 墙钟 / 到达顺序 / 采样序）画出来分析。
- 这个轴和「被测机制**真正依据**的轴」之间有一个**你没意识到的换算关系**（速率差 / 单位差 / 偏移）—— 两者不是 1:1。
- 于是数据在你的轴上呈现出「滞后」「错位」「越往后越偏」「某段干脆丢失」，你据此推出一串**运行时层**的解释
  （运行时滞后 / 状态机提前转场 / 资源在某阶段失效 / 缓存没命中…），越挖越深、还互相「印证」。
- 真相：根因是**数据层一个简单的标度 / 单位 / 时长元数据被设错了**（典型：某字段被设成 2×），在「正确的轴」上
  一眼就是「整体按一个常数因子均匀缩放」——一个常数，不是玄学。

处理：

- 「随 X 演化」的分析里，**X 轴的选取本身是一个待验证前提**（规则 7），不是中性的。先问：被测机制**真正依据**的是
  哪个量？（时序回放依据的是它内部的进度游标、不是外部计数器；流式协议依据序列号、不是抵达顺序…）用**那个**量当轴，
  不要用你最容易取到的那个。
- 优先用**系统自己拿来驱动该机制的那个字段**当测量轴（直接读它内部的进度 / 时间游标）——它和机制天然同源、没有换算混淆。
- **指纹**：若数据在你的轴上呈现「**整体按一个近似常数因子偏移 / 拉伸**」（每段都晚 ~k 倍、越后越偏、末段按比例被截断），
  第一反应不该是「运行时逐步失效」，而是「**两个轴之间差一个标度 k**」→ 去数据里找那个被设错的 duration / rate / scale / 单位字段。
- 跟模式 Q / T 的区别：Q 是字段值是条件默认占位、T 是探针没跑出空；模式 Z 是**字段值真实、探针也跑了，但你把它对着错的
  轴解读** —— artifact 出在「轴」不在「值」。跟模式 H 的关系：错轴会孵出一长串运行时推论（H 的雪球），但砍断雪球的不是
  再加一环，是**换轴**。配套：观测时序时 trace 的 gate 要选**全程不变的稳定标签**、不要选**会中途切换的瞬时标签**
  （后者把 trace 截断成假阴性，见模式 T）。具体形态见 `missing-control-points` 模式 13。

### 模式 AA：逐个元素都「单独无罪」、却漏掉它们之间的共存约束

症状：

- 你怀疑某层有问题，对该层涉事的**每个元素**单独对照 working、逐字段 / 逐字节 diff，**都干净**
  （元素 X ≈ working 兄弟、元素 Y ≈ working 兄弟、只差无关紧要的几个值甚至完全等价）
- 据此判「每个元素都对、这层无罪」，升层到更深的运行时玄学，越挖越深
- 但目标始终不达成 —— 真控制点其实还在这层、在元素**之间**

处理：

- **「每个元素单独无罪」不蕴含「它们的组合无罪」。** 当所有**单元素** diff 都干净、目标却仍失败，
  缺失的控制点可能是一条**共存约束**：两个同层兄弟元素**不能在同一时刻 / 同一独占 slot 同时活跃**，
  运行时只接纳一个、两个同时出现就互相挤掉 / 都失效。单元素对照永远照不出这种「关系层」的冲突。
- 跟模式 F（一层没查完）正好相反：F 是**单个元素**没 diff 完就升层；本模式是**每个元素都 diff 完且干净**、
  漏的是元素**之间**的关系约束。跟模式 X（多独立源）也相反：X 是「多个源各自单独都致症、删一个不够」、
  本模式是「每个单独都**无害**、只有配对 / 同时才有害」 —— 两者都在「组合」层、方向相反。
- 诊断：单元素全绿但失败时，查是否有两个元素争抢一个**同刻 / 同位的独占资源**（同一时间窗、同一锚点、
  同一单占字段、同一 channel）。修复是**解耦**（错时 / 串行 / 去重 / 分槽）、不是「修」任一元素 ——
  它们本来就没错。这跟模式 G（这层全绿目标没达成）同源：单元素全绿 ≠ 这层无罪、缺的控制点是元素间的约束。

具体形态（两个各自合法的同层元素因「同刻同独占 slot」共存而互相湮灭）见 `missing-control-points` 模式 14。

### 模式 BB：把「编译 / 转换通过」当成「行为不变」的证明

症状：做一个**本应行为不变**的大改（重构 / 模块化 / 迁移 / codemod / 重新打包 / 批量重命名），跑通**编译**或转换工具不报错，就宣布「没问题」。但编译通过只证明**结构合法**、不证明**行为等价**——移动、可见性变更、序列化改写、字段重排都能编译通过却悄悄改了语义；抽查几个点全绿也不够（模式 F）。

处理：

- **当你刻意「不改行为」时，等价性 oracle 就是「改之前的源」本身。** 把产物按**单元枚举**（函数 / 记录 / 条目 / 节点 / 配置项），对**每一个**单元跟它的改前原像做**机器 diff**，归一化掉你**有意**引入的差异（新增的可见性前缀 / 包装 / 缩进）；全等 = 行为可证明不变、差异只落在你**事先列出**的有意改动处。**不靠抽查、不靠「它编译过」、不靠肉眼扫一遍。**
- **单元集合也要逐项对账**：改前 N 个符号、改后正好 = N + 你有意增删的那几个。这顺带抓「漏搬 / 重复搬 / 搬串了」——大改最常见的静默错。
- 与模式 W 的关系：W 是「判**单个**产物的静态形态、拿已知能跑的 baseline 比」；本模式把它推到**大批量转换**——baseline 就是转换的**输入**、且要**逐单元全量 diff** 而非抽一个。两者同一信条：**事实对照 > 直觉 / 文档 / 编译器绿灯**。
- 反例（典型翻车）：把一个大文件拆成多模块，编译过 + 跑一遍没崩 → 提交；实则某个分支因可见性 / 导入解析改变走了不同路径，几周后才在边角场景暴露。逐单元 byte-diff 在提交前就会发现「这个单元的 body 跟原像不一致、而我没打算改它」。

### 模式 CC：failing 在每个可查的静态层都 == working → 差异在你没建模的运行时层、别再静态 diff

症状：你怀疑某层、把 failing 对着 working **逐层逐字段静态对比**（内容 / 覆盖 / 配置 / 加载到的数据），**每层都一模一样**——failing 和 working 在你能离线检视的每一层都全等。你却继续在静态层换角度 diff、或开始推「那一定是更深的运行时玄学」，连环假设一个接一个被实测推翻（模式 H 的极致）。

处理：

- **「failing 静态上 == working」本身是强信号**：差异**不在任何你已检视的静态层**、而在一个你**还没建模的层**——通常是**运行时的注册 / 归属 / 调度状态**（元素本身对、但没被 runtime 真正"接进"处理流程；见 `missing-control-points` 的注册/归属控制点）。静态全等 = 该停止静态 diff、转**运行时观测**。
- **运行时观测必须带正对照**（规则 7 + 模式 T）：先确认你的探针在一个**已知 working** 的同类样本上**能抓到目标信号**（working 的那条路径在 trace / 日志里确实出现），再信它对 failing 的「没出现」。没有正对照的「failing 侧没观测到」是 inconclusive、不是证据。
- **判别谓词从 working 集提、不要继续猜**（模式 S）：working 和 failing 静态全等时，唯一还没比的是**运行时被怎么对待**——把 ≥2 个 working 样本在运行时的**共性**（谁 enumerate 它、它在哪个组 / 表 / 列表里）提出来当谓词，直接验 failing 缺不缺这条。
- 反例：搬来的一个元素"不生效"，把它的内容 / 覆盖 / 依赖数据对着能生效的同类逐一 diff，全等；连推 5 个运行时假设全被推翻。真因 = 它**没被登记进 runtime 真正迭代的那个集合**（内容全对、就是没"入列"）——一个受控运行时观测 + 正对照一步锁定，比 5 轮静态推论便宜一个量级。与模式 G 的关系：G 是「这层全绿目标没达成」、CC 是「failing 和 working 在所有静态层全等」——都指向「缺的控制点在没建模的层」、CC 进一步给出「下一步是带正对照的运行时观测、不是更多静态 diff」。

### 模式 DD：改了 X 层、担心波及能力 C → 先结构定位 C 真正住哪层，别从「以为」推影响

症状：

- 你改 / 回滚了某一层的产物（二进制 / 配置 / 资产 / 某模块），然后担心「能力 C 是不是被破坏了 / 还在不在」
- 你**凭对架构的印象**判断「C 应该在这层、所以受影响 / 不受影响」，并据此行动（慌忙补回、重测、或反过来放心地跳过验证）
- 实际上 C 跟你改的那层是**解耦**的 —— C 住在另一层（数据驱动 vs 编译产物、脚本 vs 二进制、配置 vs 代码），改 X 层对 C 根本无关；或者相反，你以为无关其实正好砸中

处理：

- 「这次改动会不会波及 C」的答案来自**结构定位 C 真正的实现层**，不是来自你对系统结构的记忆 / 直觉。用结构搜索（grep 符号 / 查调用图 / 看哪层引用 / 看谁编译谁解释）把 C 钉到具体一层，再谈 blast radius
- 大量「能力」是**数据 / 脚本 / 配置驱动**的、跟二进制 / 编译产物**解耦**：改二进制不影响数据驱动的能力、改数据不影响编译逻辑。**先确认耦合关系、再判影响范围** —— 「加一项功能要不要重编 / 重部署 X」也用同一问法
- 这是 layer model 的**正向（impact-analysis）用法**：不是「故障在哪层」，而是「这个能力归哪层管」。归错层有两种代价 —— 白白回避一次本来安全的改动、或自以为安全其实破坏了它
- 证据形态：在 X 层 grep 不到 C 的实现符号 = X 层不含 C（配合模式 T 正对照：先 grep 一个你**确定**在 X 层的符号确认 grep 有效，再信「grep 不到」）。**用一次几秒的结构搜索换掉一串「应该没事吧」的猜测**
- 旁注（与模式 BB 互补）：BB 是「编译过 ≠ 行为不变」；其镜像是「**字节变了 ≠ 源 / 行为变了**」—— 同一份源经不同工具链版本重建可能产出不同字节（非确定性 build）。要「精确那个已验证的版本」用**已存的产物**、别靠重建去对记录的 hash；一个记录的 baseline hash 会因工具链漂移而失效、hash-mismatch 不蕴含「源被改了」。

### 模式 EE：行为由你改不了的外部系统 / 黑盒驱动 → 别找「配置它的数据」，找「最高可改层里调用它的 seam」

症状：

- 某行为（加载某模块 / 生成 / 进入某态 / 触发某流程）你想触发或复刻，但它由一个**你改不了的上游系统 / 运行时 / 黑盒**内部决定。
- 你到处找「哪份数据 / 配置 / 注册表控制它」—— diff 了所有可改数据层（脚本 / 参数 / 布局 / 资源），**没有一处包含那个开关**。
- 你卡在「机制未解」，或开始想深挖那个系统的内部 / 啃它的黑盒。

处理：

- 那个系统内部不可改，但它几乎总有一个**可改层的调用入口（invocation seam）**：某条「让它做这件事」的指令藏在你能改的层里（脚本 / 入口 handler / 配置）。控制点**不是**「配置它的数据」（可能根本不存在 / 是它硬编码的约定），而是**那条调用指令本身**。
- 定位路线：① 先用**基线 vs 改动版全量 diff 证明开关不在数据层**（所有可改数据层都不含触发它的开关 = 排除法坐实「由不可改系统内部决定」、别再找数据开关）；② 在**最高可改层**找谁调用了这个能力 —— 读「触发该行为的那个入口」（入口 / handler / 事件）的代码，找那条调用指令；③ 那条指令就是控制点：从你自己的入口调同一条指令即可触发 / 复刻，**无需改那个系统**。
- 阴性提醒（接模式 T）：探针「文件 / 资源放进去了但没生效」≠ 机制不存在，常是你在**错误的触发路径**下测的（那个系统只在它自己的调用路径下才激活该控制点）—— 先用「已知能触发的路径」做 positive control，再判断「不生效」。
- 跟 `missing-control-points` 模式 16（注册 / 归属：在被迭代的集合里才会被处理）配对：16 是「成员资格是控制点」；本模式是当**成员资格由不可改的系统管理**时、你加不进集合、只能找「让它把元素加进去」的那条**可改调用** —— seam 就是你能碰到的最高控制点。research-first（模式 U 旁注）在这里尤其值钱：社区 / 文档往往已记录「X 是约定 / 靠某条命令进入」，省掉整条排除法。

### 模式 FF：你「接好」的多步骤功能不生效 → 对照「完整正确流程」diff 你做了哪几步，别在你做的步骤内部找 bug

症状：

- 你按理解把一个**多步骤**功能接好了（连线 / 注册 / 配置 / 触发都做了），但功能不生效。
- 你默认「我做的某一步有 bug」，在**你已做的步骤内部**反复调（换参数、改顺序、加 patch），连续几轮都没用。
- 真相：完整正确流程有 N 步，你用的**便捷封装 / 简化路径只做了其中 M<N 步**，缺的那步（常在另一个子系统 / 另一份文件里）正是让功能生效的关键 —— 而它可能早被项目自己的 backlog / TODO / known-issues 标成「这个便捷工具不做、是 gap」。

处理：

- 功能不生效、且「该接的我都接了」时，第一动作**不是**在你做的步骤里找 bug，而是**找一个已知能用的同类样本、逐步枚举它的完整接入步骤**，跟你做的 diff —— 缺的是「哪一步」，不是「哪个值」。
- **查项目自己的 backlog / known-gaps / 流程文档**：一步到位的便捷 wiring helper 常只覆盖完整 pipeline 的一部分，遗漏的步骤经常已被显式记成「此工具不做、需手动补」。先查这个，比在你的步骤里深挖便宜一个量级。
- 与模式 O（修一个实例漏孪生）相邻：O 是「同一步在多处、漏了一处」；本模式是「完整流程多步、你整步漏了一步」。与模式 U（复用能用的工具做新操作）配对：便捷工具在常规用途上没问题、但它只做部分步骤，你的新用途需要它不做的那步。
- 决定性对照永远是「working 样本的**完整步骤清单**」vs「你的步骤清单」—— 不是「我觉得这步应该够了」。

### 模式 GG：成功判据只有人能观测（呈现效果 / 交互体感 / 整体观感）→ 暴露 config + 按反馈迭代，别猜-部署循环

症状：

- 你要把一个产物调到「对」，但「对」的判据**只有人能观测**（布局位置 / 呈现效果 / 交互体感 / 整体观感），你这侧只能读**静态数据**、看不到运行时的人类可感结果
- 你**猜一个值 → 部署 → 等人看 → 不对 → 再猜一个值**，每轮 cost 高（部署 + 人实测），且你在盲猜（看不到运行时呈现）

处理：

- 当**验证 oracle 在人那侧**、你只能读静态数据时，不要 guess-deploy 循环。① 把要调的量**抽成一个 config**（每项一行：哪个产物的哪个属性 = 什么值）；② 用你**能离线读到**的信息**预填**它（产物锚定在哪 / 源的 authored 值 / 已知 working 同类的值），给一个有依据的起点而非乱猜；③ 把「人的反馈」当成你缺的那个 oracle —— 人看运行时呈现报「长了 / 短了 / 偏了 / 不像」，你改 config 一行，**不重跑整条构建**
- 关键转变：**人是你缺的那台测量仪**。与其在数据侧盲猜逼近，不如把「数据侧能读的」和「人侧能看的」对接 —— 你出**可解释的预填 + 可单行调的旋钮**，人出**每项的方向信号**，合力收敛，比单方 guess-deploy 快一个量级
- 预填要标依据（「这个值来自源 authored / 来自 working 同类 / 纯占位默认」），让人调时知道哪些是可信起点、哪些待定
- 跟模式 N 互补：N 是「连续失败 → 转离线深挖找结构」；本模式是「判据本就在人侧、离线也看不到运行时呈现 → 把人变成 oracle、用 config 把回合 cost 压到最低」。两者都在砍「贵的在线试错循环」，N 转向离线分析、GG 转向人机协作的 config 旋钮。

### 模式 HH：删一个「看着没人引用」的东西 → 只在你能检视的层成立；不透明层是盲区、结构检查 ≠ 语义安全

症状：

- 你要删一个看着 orphan 的东西（某资源 / 记录 / 字段 / 条目）。你审计了**所有你能检视的层**（grep
  代码、dump 数据、查可读引用），都没引用它 → 判「孤儿、可删」→ 删
- 你还对「删这个动作」做了**结构完整性检查**（改完产物仍 well-formed / `serialize(parse(x))` 对未改
  部分字节恒等），通过了 → 更确信删对了
- 结果在一个**更晚的运行时点**崩 / 坏 —— 某个层仍在引用你删掉的东西

处理：

- 你的「没人引用」结论**只覆盖你能读的层**。系统里若存在一个**不透明 / 不可检视的层**（二进制 /
  黑盒 / 编译产物 / 外部系统的内部状态），它可能仍引用那个「孤儿」，而你的静态审计照不到。
  **「在我能检视的层里看着 orphan」≠「真没人引用」** —— 后者在有不可检视层时是**未证明的推论**
  （规则 7），别当事实
- **结构检查 ≠ 语义安全**：结构 / round-trip 检查只证明「你的编辑没把产物写坏」，**不证明「被删的
  东西没人依赖」**。这是两个独立命题，别拿前者的绿灯当后者的证据（呼应模式 U 的字节恒等：它验
  serializer 没写坏、不验你删的内容是不是承重）
- 正确流程：① 删 orphan 前，把系统**所有层**列出来、标哪些你**能检视**、哪些**不能**；只要有不可检视
  层、「unreferenced」就先当推论。② 不可检视层无法静态确认时，唯一可信验证是**运行时**：删一个、在
  「会暴露悬挂引用」的那个运行时点验一次，再删下一个。③ **别把多个破坏性删除批在一次 verify 之前**
  —— 一旦崩，无法二分是哪一删致命（规则 4 单变量的删除版）；先留一个**已知好的还原点**（版本快照 /
  改前基线），崩了按子集回滚二分（模式 Y / J）
- **「看着是孤儿」也可能本就该留**：它在不可检视层有承重引用、而动那个层的代价极高（若是二进制黑盒、
  可能根本没有安全编辑工具）。这时正确决定是**留着**（标注「inert 但被不可检视层引用、动不了」），
  不是硬删 —— 一个之前判过「harmless 留」的标记，往往正是有人已经撞过这堵墙的记录，别轻易翻案
- 跟模式 F（一层没查完就宣布无罪）相邻：F 是「该层我没查完」、本模式是「有**整整一层我根本没法查**」；
  跟模式 DD（结构定位能力住哪层）互补：DD 正向问「这能力归哪层」、本模式反向防「我以为没人引用、其实
  有个我看不见的层引用着」

### 模式 II：把某层判成「墙 / 需深层不可改手术」→ 先验更高可改层能不能开那个闸，别直接接受「墙」

症状：某能力「做不到」，你归因为「底层状态机 / 二进制 / 黑盒里没有那条路径，要做深层手术才行」，于是放弃、或转去啃最硬的那层。但**「这是堵墙」是待验推论、不是结论**（规则 7）—— 很多「墙」其实是**你没找对控制点**：真正决定「能不能」的是某个**谓词读的一个解锁标志 / 配置位**，而那个标志**可由更高的、你能改的数据层打开**（一个时间线 / 描述符里的事件、一行配置、一个信号），根本不用动黑盒。

处理：

- **先找那个 gate 谓词，看它实际读什么**：「能不能做 X」背后通常有个布尔判定。读它的实现 —— 往往是「当前状态有没有解锁 X」一类的 **unlock flag 查询**，不是硬编码在状态图里的一条边。flag ≠ 边：边要改图（可能真是墙），flag 只要有谁去置位。
- **查这个 flag 由谁置位、最高能在哪层置**：若它由**数据层（你能编辑）**的某个事件 / 标记置位 → 你在数据层加上那个置位物，闸就开了，墙不存在。沿用一个**已知能做 X 的样本**，看它凭什么过了同一个谓词（它的数据里有什么你的没有）—— 那个差异就是开闸的控制点（呼应模式 S：从 working 提判别物）。
- **只有当 flag 确实只由不可改层置位、且无可复用的 seam（模式 EE）时，才是真墙**。
- 判据：下「这是墙 / 要深层手术」结论前，必须能回答「那个 gate 谓词读的标志，最高能在哪一层置位？我验过那层改不动吗？」答不上 = 你在没验证的推论上放弃、可能放弃在离答案一步之遥处。
- 跟模式 EE 对照：EE 是「行为**确**由黑盒驱动 → 找调用它的 seam」；本模式更前一步 —— **先别信「是黑盒 / 墙」这个判断本身**，那个闸常常在你能改的数据层就能开。两者一前一后：先用本模式证伪「墙」，证不伪再用 EE 找 seam。

### 模式 JJ：移除实验「阴性」就判「无关」→ 但你测的表面信号可能由多机制共同产生、且看不见被移除项真正控制的属性

症状：

- 你怀疑 X 导致某现象，做**移除实验**（拿掉 X / 把某个值改回默认），观察那个现象——**没变**，于是判「X 与此现象无关」、升层去别处找因。
- 但你观察的那个**表面信号**其实由**两个独立机制**共同产生：X 控制其中一个、另一个机制（你没建模的）单独也能让表面维持原样。移除 X 时另一个机制照旧 → 表面不动 → 你误以为 X 无关。
- 更隐蔽的一层：X 真正控制的是**另一个属性**，而那个属性在你测的表面信号里**根本不可见**（「X 在」和「X 不在」两种情况表面长得一模一样、区别在一个你没去测的量上）。

处理：

- **移除实验的「阴性」只有在你的 observable 真能区分被移除项的效果时才成立。** 动手移除前先回答两个问题：① 这个现象**只由 X 产生**吗、还是有第二个机制也能产生同样的表面？② X 真正改的那个属性、在我观察的量里**看得见**吗？
- 表面信号可能被多机制共同维持时 → 换一个**判别性 observable**：一个**只有被移除项会影响**的量（X 专属的副作用 / 次级状态）。移除 X 后看**那个量**动没动、才是干净的因果判定。
- 典型形态：同一个表面（「进入了某状态 / 触发了某流程 / 输出了某值」）既来自一个**固有行为**（移除 X 不影响它）、又来自 X 控制的**判定 / 属性**——两者表面同形。这时「移除 X、表面没变」完全可能是「固有行为还在产生这个表面」、而 X 控制的判定属性你压根没测。
- 跟模式 J 的区别：J 是**正向 post-hoc**（改动后出故障 → 默认改动致故障）；本模式是**反向 post-hoc**（移除后现象没变 → 默认移除项无关）—— 同一个病根：单变量实验的 observable 选错 / 覆盖不全。跟模式 X 的区别：X 是「多个独立源各自单独都致**同一**症状、逐个删都还在 → 误判整层无罪」；本模式是「一个表面由多机制共同维持、且被移除项控制的是**另一个不可见属性** → 误判该项无关」。三者（J / X / JJ）合起来：**任何「单变量实验阴性 ⇒ 下结论」都要先验「我的 observable 是否干净、单一、且真能区分这个变量的效果」。**

### 模式 KK：反复在「你怀疑的子系统」内二分、真凶在一个你从没变过的子系统 —— 隔离空间按「与 working reference 的完整 delta」圈定、不是按「我以为是谁」

症状：

- 一个持续存在的故障。你做单变量隔离：把**子系统 A** 的组件逐个换成 baseline（改回默认 / 换干净版 / 关掉某开关），每次都测。有个「全 baseline 对照」看起来正常。
- 但你**每一次实验都只变 A 的组件**，另一个**子系统 B**（你从没怀疑过、所以从没动过）**在所有实验里恒定**。真凶是 B 的一个组件。
- 结果：变 A 永远不 fix → 你消元出「是 A、而且表面换 A 的组件都没用 ⇒ 病根在 A 的**深层 / 够不着的内部**（一堵墙）」，然后投多轮去深挖 A 的内部（啃底层 / 解黑盒 / 造工具）。**一个错误前提能撑十几轮。**
- 更坑的一层：那个「全 baseline 对照」靠一个**全局开关**达成（禁用全部改动 / 安全模式 / 关掉某 feature-flag），而这个开关**顺带关掉了故障所在的那条特性 / 场景本身** → 对照跑的是**另一个（良性）场景**，「对照正常」被误读成「环境 / B 没问题、是我改的 A」—— 一个被污染的 control（模式 J + R 的合体）。

处理：

- **隔离空间按「与 working reference 的完整 delta」圈定，不是按怀疑圈定。** 二分前先**机械枚举你的配置相对已知可用参照改动的每一个组件**（每个被覆盖 / 新增 / 删除的文件 · 配置 · 资源 · 开关）—— 真凶一定在这个 delta 里。只二分 delta 的一个**子集**（你怀疑的那部分），永远找不到落在其余部分的真凶。
- **「反复变 A 都不 fix」本身就是真凶在 A 之外的证据。** 当你发现「我一直改 A、从来没用」，别升级成「那 A 的病根一定更深」——**掉头问「我从来没变过什么？」**（full delta 里 A 的补集）。N 轮 modify-suspect-A 全阴性 ≈ 强烈提示换子系统（呼应模式 N：贵循环转向）。
- **验证对照真的在跑同一个 failing 场景。** 一个靠「禁用特性」达成 clean 的开关，可能**悄悄换掉了跑的是哪个场景**。确认对照确实复现了同一条 failing 路径（同触发、同特性 active），否则「对照正常」对你的改动**什么都没证明**（模式 J 的具体陷阱、模式 R 的近亲）。
- 决定性动作 = **二分整个 full delta**（把所有改动的组件对半分、不是只分你怀疑的 A）→ 失败的那半含真凶 → 递归。这能找到你从没怀疑过的子系统里的真凶。
- 跟模式 X 的区别：X 是「你**正在变**的那一层里有多个独立源、逐个删都阴性 → 误判整层无罪」；本模式是「真凶在一个你**从没变过**的子系统、整个隔离都在错的子集里打转」。跟模式 F 的关系：F 是「一层没查完」，本模式是「**整个子系统从没进入过隔离空间**」—— 同一病根（覆盖不全）在更大尺度上的版本。

### 模式 LL：你追踪的判别信号在 failing 案例里从不出现、症状却持续 → 信号选错、缺陷在一条平行通道

症状：

- 你挑了一个信号（某字段 / id / 标志 / 日志值）当作某 bug 的**判别器**，一轮轮盯着它分析、甚至据它设计实验。
- 但这个信号只在 **working / 合法路径**里取到那个「值得注意的值」，在你正诊断的 **failing 案例里从不出现** —— 症状却明明还在。
- 你还是继续盯这个信号（因为它「看起来相关」），甚至连续跨多轮 / 多个 modify 实验都建在「这个信号=病根」的前提上。

处理：

- **一个症状可以由一条你选的信号根本不覆盖的通道产生。**「我的信号在 failing 里从没触发、可症状就在眼前」= 强证据说明**信号选错了**、真缺陷在一条**平行通道**：可能是另一个字段，也可能是**一个被正确报告的标识符背后的实际内容**。路由 / 状态 / 身份可以**完全正确**、而它加载 / 引用的**叶子内容（字节 / 资源本体）是错的** —— 你那个「身份级」信号照不出这种「内容级」缺陷。
- **利益相关者的一句 reframe（「那不一定是你说的信号 —— 只是个长得像它的东西」）是经典的 tell**，把它当**优先级中断**（模式 I）：立刻停下当前分析。
- 下一步：**停止追踪这个信号**，枚举「还有哪些通道能产生这个症状」（并行事件类型 模式 20、或「一个正确标识符背后的字节内容」），去验那些。
- 关系：模式 20（一层有多条平行通道、工具只 surface 一种）—— LL 是它的「运行时信号」形态。模式 CC（failing 静态全等 working → 转运行时观测）—— LL 更锐：**连运行时路由都和 working 一致、只有叶子内容不同**。模式 Q/T（别把探针输出当地面真值）—— LL 是「别默认你挑的那个字段就是对的判别器」。

### 模式 MM：靠「复活一个旧快照」来重新启用一个曾撤下的能力 → 拿到那个时点的状态、丢掉之后所有修复

症状：

- 某个能力/特性之前被**撤下 / 回退 / 禁用**了（为了发布、为了隔离、为了简化）。现在你想**重新启用**它。
- 你图省事，直接**复活一个「当时带着这个能力的旧快照」**——旧 commit / 旧备份 / 旧配置 / 旧分支 / 缓存副本——把它 restore 回来。
- 结果：这个能力**连同它当时的 bug 一起回来了**。因为你 restore 的是「该能力在**那个时点**的状态」，而不是「该能力**最新修好**的状态」——在那个快照之后才打的修复（可能还散在**别的文件**里、被同一次撤下一起回退了）全丢了。

处理：

- **「一个旧快照里有能力 X」≠「能力 X 的当前正确形态」**。旧快照 = 能力 X **截至那个时点**、缺失之后所有 refine/fix。尤其危险：撤下一个能力时往往**同时回退了它散在多个文件里的修复**（主逻辑 + 配套的参数 / 数据 / 阈值）；你只 restore 主逻辑那个快照，配套修复不会自己回来。
- **正解 = 从「当前已知正确的基线」重新派生这个能力，而不是 resurrect 旧 artifact**。把该能力**拆成它依赖的各个控制点**（主逻辑、参数、数据、开关），逐个在**当前**基线上重新施加到**最新修好的值**——而不是整块搬回一个历史状态。
- **验证锚点用「最新正确态」、不是「那个旧快照」**：restore 完先对照「这个能力最后一次被确认好用时的完整控制点清单」逐条查，缺一条修复就是一个待复发的 bug。
- 关系：模式 M（推论级 close 可能错、别当 settled）的**工件版**——M 是「别把旧结论当现状」、MM 是「别把旧工件当现状」。模式 DD 旁注（字节变了≠源变了、非确定性 build）的**反向**——那里是「同源不同工件」、这里是「旧工件缺了后续对源的修复」。共同信条：**任何「历史状态」都要问一句「它落后于当前正确态多少」再用**。

## 代理自约束

如果你开始反复说这些话，就说明该触发本 skill：

- 「再试一次」
- 「可能是这个参数」
- 「先改这里看看」
- 「先让用户再测一下」
- 「我大概知道方向了，先做一版」

这通常说明你已经回到局部试错，而不是在缩小问题空间。

## 会后复盘

如果这次已经打转，结束前补一段：

- 我打转在哪一层
- 为什么会打转
- 哪条可信层级没有被及时接管
- 下次在第几步就该停下来

把这段复盘写回 skill 或项目文档，而不是只留在对话里。
